# Homelab Probe

Fork of [ericfitz/unifi-clients-export](https://github.com/ericfitz/unifi-clients-export), being extended into a tool for querying, troubleshooting and inventorying a UniFi Network controller. Keep the Apache-2.0 license and upstream credit.

## Layout

- `hlp.py`: thin launcher; all logic lives in `homelab_probe/`.
- `homelab_probe/config.py`: env/`.env` loading. `client.py`: `UniFiClient`, the only place that makes HTTP calls. `snapshot.py`: `collect_snapshot(client, site, Needs(...))`, the one read of the controller; a command declares what it reads with a `Needs` (and an `EventQuery` for the event log), never with loose flags. `export.py`, `query.py`, `reservations.py`, `new_clients.py`, `client_view.py`, `events.py`, `wan.py`, `firewall.py`, `audit.py`, `wifi.py`, `topology.py`, `history.py` and the `diagnose/` package: pure functions over a `Snapshot`. `diagnose/` has one module per topic (`devices`, `health`, `addresses`, `reserved`, `ports`, `wireless`, `event_checks`, plus `model` for severities, codes and `Finding`, `output`, and `areas`); a new check is a function in the module of its topic, a code in `model.CODES`, and one line in `areas.CHECKS` with every area it can emit (the order there is part of the output). `areas.py` maps code prefixes to the areas of `diagnose --only/--skip` (`devices`, `health`, `wan`, `clients`, `reservations`, `ports`, `wifi`, `events`) and `needs_for` says what a selection reads: a new code needs its prefix in `AREAS`, and a check that starts using new snapshot data must be reflected in `needs_for` (`tests/test_diagnose_areas.py` runs every area on the minimal reads and compares with the full run, so a missing read fails). `util.py`: shared helpers: output safety (`printable`, `clean_data`, `safe_output`, `csv_safe`) and small value helpers (`number`, `number_or_zero`, `known_percent`, `plural`, `normalize_mac`, `hex_digits`, `epoch_text`, `format_time`, `search_rows`, `is_randomized_mac`, `describe_age`). `demo/`: the synthetic controller (`controller.json` plus `DemoSession`, which the tests call `FakeSession`; `demo_config`/`demo_client` build the configuration and client of `--demo`). `documents.py`: documents, the layer between reading and printing (`Document(name, data, warnings)`: `data` is the dict `--json` prints, `x_document(client, site, params, settings, echo)` reads the snapshot with the command's `Needs` constant inside `logs.collect_warnings` and builds it; `wan`, `wifi`, `topology`, `firewall`, `audit`, `events`, `client`, `query`, `new-clients`, `diagnose`, `snapshot`, `diff`, `export`, `info` and `doctor` are converted (every command); `diagnose` also has `meta["complete"]` (False when an optional read failed, which `--watch` skips), and `--notify` and `--watch` take their `Finding`s from `findings_from_document(document.data)`; `data` is a list for a `--json` that is a bare array, and `meta` carries what only the text view needs (`events`: `more`, `cap_truncated`; `client`: the `matches` when it is not exactly one; `query`: `kind`, `offline`); `audit` builds its document with `diagnose.findings_document` and renders it with `render_findings`, which #181 reuses for `diagnose`). `serve` network exposure (`--host`, `--allowed-host`, `--forwarded-allow-ips`; the helpers `util.check_bind`/`parse_allowed_host`/`parse_forwarded_ips` run without the extra: a wildcard bind needs an allowed host, the `Host` list is never a wildcard, `*` is never a trusted proxy, and the default trusts no forwarded header), `server/auth.py` (login: `guard` is the dependency of the **whole app** and lets through only the endpoints marked `@public`, so a route nobody declared needs a session; `admin` adds the stricter role; `OriginGuard` is a middleware refusing an unsafe request whose `Origin` is not the `Host` or whose body is not JSON; `sessions.SessionStore` keeps hashes of the cookie values in memory and re-checks the account, its role and a fingerprint of its password hash on every request; `throttle.LoginThrottle`; never write a typed username that is not an account, a password or a session id to a log or the audit trail; `app.routes` shows FastAPI's included routers as opaque objects, so enumerate routes through the OpenAPI document, not `isinstance(r, APIRoute)`), `server/` (the `web` extra: `fastapi`, `uvicorn`; the core never imports it, `tests/test_server_boundary.py` checks that, and `hlp serve` imports `server.runner` inside its handler): `app.create_app` (the factory), `security` (the `Host` allow-list, the headers on every response; the bind and proxy checks are `util.check_bind`, `bind_host_name`, `parse_allowed_host` and `parse_forwarded_ips`, so the command checks `--host`, `--allowed-host` and `--forwarded-allow-ips` without the extra, and `allowed_hosts` re-validates its input so a caller that skips argparse cannot open the list), the request log (`server.request`, the route template, never the path), `runner.run`, `routes` (one GET per document; each calls the document function the command calls through `ControllerService.build`, validates its parameters like the CLI and returns the document plus `generated_at`/`warnings`, or `{items, ...}` for a bare array; a route never takes a path to forward, and an error is `errors.ApiError` with a fixed sentence, never an exception's text), `apischema` (the schemas of `docs/schemas`, shipped in the wheel as `homelab_probe/schemas` through `[tool.setuptools.package-dir]`, so `[tool.setuptools] packages` is a hand-kept list that `tests/test_accuracy.py` checks; `tests/golden/openapi.json` is the OpenAPI snapshot: `UPDATE_GOLDEN=1 uv run pytest tests/test_server_routes.py`), `cache.ResponseCache` (a TTL, single-flight per key, stale-on-error, error coalescing, a cap on reads in flight; answers are deep-copied in and out) and `service.ControllerService` (a `CachingClient` per document build, sharing one cookie-less session and the cache; `CachingClient` overrides only `_get` and `_post_system_log`, so documents and snapshots are unchanged and a new read needs no server code; `build()` returns the document with `generated_at` and warnings). Tests use `fastapi.testclient` with `httpx2`, and CI syncs the extra everywhere except the `base-install` job. `setup.py`: the engine of the guided setup, shared by `hlp init` and the web wizard (core, no new dependency; validates one setting at a time with the validators the commands use, merges settings into an existing `.env` keeping everything else, writes owner-only files atomically with a `.bak`, refuses symlinks, values with a line break or `${`, and never puts a secret in a result or message; `config.build_config`/`read_env_values`/`layered_values` are the pure readers it and the server's reload use, `doctor.check_controller` the connection test). `tlsprobe.py`: the setup's two TLS steps (`fetch_certificate` completes an unverified handshake and sends nothing, `check_pin` trusts only that certificate through the context `requests` builds for `verify=<file>`, `resolve_target` refuses addresses no controller has and every address a name resolves to must pass; failures are `ProbeError` with a fixed `reason`, never library text; the test servers are `tests/tls_fixtures.py`, whose keys are stored without their PEM header lines so no file looks like a leaked key). `server/wizard.py`: the setup mode of a server with no usable settings (`SetupState` holds the token and the in-memory `Draft`; `auth.setup_ok` marks the seven setup endpoints, which `guard` lets through while `app.state.setup.mode` is set and every other endpoint answers 503 `not_configured`; `setup_access` wants the `X-Setup-Token` (throttled and audited like a login, via the `(setup)` actor) while no enabled administrator exists and an administrator's session otherwise, or once `mode` is None; setup mode applies only when neither `UNIFI_URL` nor `UNIFI_API_KEY` is set, broken settings stay a loud start-up error (owner decision, #185); link-local addresses are refused even though the issue text lists them, because 169.254.169.254 is the cloud metadata address, and `--allow-public-controller` is the opt-in for public ones; the key is registered with `logs.register_secrets` on arrival and never returned; connection tests use `max_redirects = 0` and fixed-word results; `runner.resolve_config` reads `--env-file` > `HLP_ENV` > `<data-dir>/.env` plus the environment without mutating it, and `serve` is a `run_local` command for that reason; `commands.apply_logging` is the secret registration and log setup `cli.main` also uses). `/finish` writes through `setup.apply` (plus `certs/controller.pem`), creates the administrator last, reloads through `SetupState.reload` (the closure `commands._run_serve` gives `runner.run`: the same resolution and `--timeout`/`--parallel` overrides as at start), starts a `ControllerService` and sets `mode` to None; when the environment, `--env-file`/`HLP_ENV` or the volume would defeat the saved file it writes nothing and returns the finished `.env` and compose snippet with `setup.PLACEHOLDER_KEY` instead of the key (the key is never returned, owner decision #185). A configured server with no enabled administrator starts in `MODE_ADMIN` (only `status` and `finish`; `runner.run` makes the state) instead of exiting. `server/settings_api.py`: `GET`/`PUT /api/v1/settings` edit the same `hlp.toml` the CLI reads (`settings_file`: `--config`, else `<data-dir>/hlp.toml`, which the report routes use too): the change is applied to the text with `tomlkit` (the `web` extra, never imported by the core), written to a temp file named `hlp.toml` and loaded with `settings.load_settings` (its message is the 422), a `version` hash detects an edit made meanwhile (checked again just before the write, under a lock), the old file is `.bak`, permissions are kept, a symlink is refused, a no-op writes nothing; a write route is marked `@local_write` and `serve --read-only` makes `refuse_if_read_only` answer 403 for it (`tests/test_server_read_only.py` lists every unsafe route and fails on one that is neither marked nor on its `WRITES_NOTHING` list). `server/snapshots_api.py`: `GET`/`POST .../snapshots` and `GET .../diff` over the files `snapshot`/`diff` use (`history.site_snapshots`, `find_snapshot`, `snapshot_summary`; the site is resolved first through the cached `client.resolve_site`, its id names the directory; a snapshot is addressed only by a name that passes `history.is_snapshot_name`, so no caller path is opened; the save refreshes the cache first, runs under a lock with its prune, is `@local_write` and admin-only and audited as `snapshot.saved`). `routes.respond` and `routes.checked_site` are the shared helpers of the site routes. `server/users_api.py`: `/api/v1/users` (admin-only, `@local_write`) over `AccountStore`; `accounts.py` raises typed errors (`PolicyError`, `UserExistsError`, `NoSuchUserError`, `LastAdministratorError`, `AdministratorExistsError`, `AuditWriteError`, all `AccountError`) so the API maps them by kind and never by message (`PolicyError.code` picks a fixed sentence in `errors.POLICY_MESSAGES`; never pass `str(error)` of an account error to a response), and `AccountStore.update(username, role, disabled, on_change(old, new))` changes both fields atomically; `errors.ERROR_SCHEMA`/`error_responses(..., text={404: ...})` build the error entries of the OpenAPI document with the wording of each route. `server/scheduler.py`: `serve --scheduler` runs the diagnose and snapshot jobs on a thread (`Scheduler.tick()` is the testable unit with an injectable clock; it never raises: a job failure is a `JobResult` with a fixed reason). The notification step is `notify.process`, shared with `diagnose --notify` and taken under `util.file_lock` on `<state>.lock` (a scheduler and cron never both announce; `baseline_if_new` makes the first scheduled run baseline instead of announcing all; the scheduler skips the state entirely on a partial read and never writes it through a symlink); `snapshots_api.store_snapshot` is the save-and-prune shared with the route. Run records are `scheduler.run` events with a fixed reason: never put a message, name or address in one. A new setup route needs `@setup_ok`, a case in `tests/test_server_setup.py` and an audit event named in `docs/web.md`. `accounts.py`: the accounts of the web interface and `hlp web-user` (standard library only; `AccountStore` keeps `users.json` under a lock file with atomic writes, scrypt hashes carry their parameters and are upgraded at login, the last enabled admin is protected inside `AccountStore._change` so no path bypasses it, `LocalAccounts` is the first `Authenticator`; `AuditLog` writes the rotated, owner-only `audit.log`; a store method is never named `delete`, `tests/test_events.py` greps the package for HTTP verbs; a new audit action goes in `docs/web.md`). `doctor.py`: the `doctor` checks of the tool's own setup (a `Check` has a stable `id` from `CHECKS`, a status and a message built from fixed words; it runs with `Command.run_local` because a broken configuration is what it reports, and never repeats an address or a secret: a failed request is explained from `UniFiAPIError.kind`, not from its text). `logs.py`: the `homelab_probe` logger tree (formats `cli`, `text`, `json`; the redaction filter; request ids; `EVENTS`; `warn` and `collect_warnings`). `notify.py`: notifications (plan what changed, wording, the one outbound `requests.post`, state file). `watch.py`: `diagnose --watch` (what changed since the last pass, from `notify.plan` with an in-memory state; the loop and its injectable `commands.WATCH_SLEEP` are in `commands.py`; never combined with `--json` or `--notify`, and it must not write or send anything). `settings.py`: `diagnose` thresholds and ignore rules from an optional TOML file; new checks take their thresholds from `DiagnoseSettings`, never module constants. `cli.py`: the argument parser and `main` (config, client, then the command's handler). `commands.py`: one section per subcommand (its arguments, its checks, its handler, the `Needs` it declares) and the `COMMANDS` registry.
- `tools/`: development scripts that are not part of the package: `record_fixture.py` (records a real controller into a sanitised fixture) and `sanitize.py` (the deterministic sanitiser and its leak check). `tests/contract.py` is the one table of the fields the code reads from each endpoint (also the request guard `RecordingSession` and `endpoint_of`); `tests/field_tracking.py` derives that list from what the code actually touches.
- New features are new subcommands: a section in `commands.py` (`_add_x` for the arguments, `_check_x` for combinations to reject, `_run_x(ctx) -> int` for the handler, which declares its `Needs`) plus one `Command(...)` row in `COMMANDS`, backed by modules that take a `Snapshot`; keep fetching (snapshot), analysis and output separate.
- Shell completion (`completion.py`): the bash, zsh and fish scripts are generated from the argument parser, so a new option needs nothing and a value argparse cannot express goes in `VALUE_HINTS`; `hlp completion SHELL` is the command that runs through `Command.run_local`, before any `.env` is read, so it works on a machine with no configuration. `tests/test_completion.py` runs the bash script in a real bash and checks that every command and option is in every script.

## Commands

- Run: `uv run hlp.py <export|query|client|new-clients|diagnose|events|wan|firewall|audit|wifi|topology|snapshot|diff|doctor|completion|web-user|info>`
- Tests: `uv run pytest`. Lint: `uv run ruff check .` (add `--fix` for import order and unused imports). Types: `uv run mypy` (clean, and blocking in CI: fix a finding with a real narrowing or type, not a `# type: ignore`, which `warn_unused_ignores` would also police). The shapes worth naming are `TypedDict`s: the saved snapshot (`history.SnapshotRecord` with `DeviceRecord`, `ClientRecord`, `ReservationRecord`; `Diff`/`DiffPart`/`Change`), the topology (`topology.Topology`, `Node`, `Summary`) and the Wi-Fi rows (`wifi.Radio`, `Neighbor`). Controller payloads (`Snapshot.devices`, `legacy_clients`, ...) stay `Dict[str, Any]` on purpose: they are undocumented and vary by model, so typing them would claim knowledge we do not have. A record that is read back from disk (`load_snapshot`) is validated first and then cast, because `isinstance` cannot check a `TypedDict`. When you add a key to one of these, add it to the TypedDict: `tests/test_typed_records.py` compares each TypedDict with the keys of a real capture, tree and radio/neighbor list (Python 3.10 has no `NotRequired`, so a key that exists only sometimes goes in a `total=False` subclass, as `Node` does); use `util.record_for` to look up a record by an id that may be missing. Lockfile: `uv lock --check`. CI (`.github/workflows/ci.yml`) runs all of these on every push to `main` and every PR, tests on Python 3.10 to 3.13; run `uv run pytest` and `uv run ruff check .` before pushing. The minimum Python is 3.10.

## Documentation

- **The README is the quickstart; the detail is in `docs/`.** Every new feature is documented in the same PR in both places: in `README.md` a row in the Commands table (with its `[details]` link), one usage example in the Usage block and, for a command, a one-line stub under the same heading as before with a link; in the `docs/` page of its group the section (columns, filters, data sources, caveats, sample output, the code table for new finding codes), the layout block of `docs/development.md` if you add a module, and a `--help`-accurate list of flags. The pages are `diagnose.md` (diagnose and audit), `notifications.md`, `scheduling.md` (cron, systemd, launchd and Docker: every snippet is run by `tests/test_docs_scheduling.py` or was run by hand, so change them together with the code they depend on, such as exit codes and the default state file), `inventory.md` (query, export, snapshot, diff, new-clients), `network.md` (topology, wifi, wan, firewall, events, client), `configuration.md` (settings, `--verbose`, troubleshooting), `examples.md`, `features.md` and `development.md`; a new page must be linked from the README. Keep the README under 250 lines (`tests/test_docs_layout.py`), never delete a heading without moving it (every anchor the README ever had must exist somewhere, so old links keep working) and use only relative links that resolve (the same test checks them). Changed behavior (flags, output columns, exit codes) updates the existing text too.
- `SECURITY.md`, `CONTRIBUTING.md` and `.github/ISSUE_TEMPLATE/` (two issue forms and `config.yml`) are the community files; `tests/test_community_files.py` checks their links, the form schema, that every example address is made up, and that the commands `CONTRIBUTING.md` lists are the ones CI runs. When a rule here changes (a command CI runs, the README ceiling, the Python floor, a label, the supported versions), change them too. Private vulnerability reporting is a repository setting only the owner can switch on (the `SECURITY.md` link needs it).
- Keep `CLAUDE.md` current when adding a module or subcommand (Layout, Commands) or learning something non-obvious about the API.
- Example output in docs must come from the synthetic fixture, never from a real network.
- Before opening a PR, check that the README and `docs/` match `hlp <command> --help` (`tests/test_docs_drift.py` checks the options).
- Every user-visible change (a command, a flag, an output column, a check, a setting, a fix people would notice) gets a line in `CHANGELOG.md`, under the entry that is still marked `Unreleased` (after a release, open a new `## [Unreleased]` heading above the last one). A change to an exit code, a finding code or a JSON `version` must be called out; `tests/test_changelog.py` fails if a command or a finding code named there does not exist, or a command is missing from it.

## Conventions

- Names (the project was renamed before its first release; see #160): the project and distribution are `homelab-probe`, the Python package `homelab_probe`, the command `hlp` (launcher `hlp.py`), the settings file `hlp.toml`, the variable naming the `.env` file `HLP_ENV`. **UniFi is the primary and, for now, only supported platform** (more may come, see "Platforms" in #160): its connection settings are prefixed `UNIFI_` (`UNIFI_URL`, `UNIFI_API_KEY`, `UNIFI_SITE_ID`, `UNIFI_VERIFY_SSL`, `UNIFI_TIMEOUT`, `UNIFI_PARALLEL_REQUESTS`) and a later platform gets its own prefix; `ALLOW_INSECURE_HTTP`, `NOTIFY_*`, `LOG_*` and `HLP_ENV` are shared. Finding codes are never renamed, so UniFi's stay unprefixed and another platform's codes must carry its name (`proxmox.vm.stopped`); nothing UniFi-specific goes into a name that every platform would share. Do not write the old names (`tests/test_project_name.py` fails on them) and do not widen the "tested on Network 10.6.106" claim.
- Documents (`documents.py`, issue #178): a new command is a builder plus renderers, never a handler that prints data: `build_x(snapshot, ...)` (pure, in its module), `x_document(...)` in `documents.py` (reads with a `Needs` constant, returns a `Document` whose `data` is exactly what `--json` prints, `version` first, JSON-serializable, raw values), and a handler that only parses, calls the document function, renders `document.data` and prints. The text renderer takes the dict, so `--json`, the text and a later API cannot drift; warnings are in `document.warnings` (`echo=True` on the command line keeps `Warning:` on stderr in the same order, `echo=False` for an API). `documents.py` prints nothing and imports only the standard library and this package (never `server/`, never a third-party package; `tests/test_documents.py` checks both).
- Reading the controller: a new read is a new field of `snapshot.Needs` plus the code that honors it, and every command passes the smallest `Needs` it uses (`tests/test_needs.py` pins which endpoints each command reads, so a command that starts reading more fails the suite until its declaration and the test agree). Required data (`users_required`) fails the command; everything else degrades with a warning.
- Shared helpers live in `util.py` and are imported; do not define a private copy of one in a module (the same `_num` once existed in five places), and do not import another module's underscore-prefixed names. `tests/test_util_helpers.py` tests them directly.
- Stdlib `csv`, not pandas. Match the surrounding style; type-hint public functions.
- Configuration (`config.py`): the `.env` file comes from `--env-file`, then `HLP_ENV`, then `./.env` in the current directory only (never the package directory or parent directories). Validate every setting (`UNIFI_VERIFY_SSL` words, `UNIFI_SITE_ID` characters (and `--site`, which beats `UNIFI_SITE_ID` and goes through the same `validate_site`, naming the option in its messages), `UNIFI_URL` scheme and host, `http://` only with `ALLOW_INSECURE_HTTP`) and percent-encode site references in URL paths. The API key is never printed: `Config.api_key` is `repr=False`, `UniFiClient._redact` strips it from response bodies and exception text, and a loose-permission `.env` gives a warning (`Config.warnings`, printed by `cli.main`), never an error. Any new message built from a response or an exception goes through `_redact`.
- Output safety (`util.py`): names (clients, devices, SSIDs, event text) are untrusted. Text renderers call `clean_data` on their report (or `printable` on single values; `format_table` cleans every cell), every CSV cell goes through `csv_safe` (for output that reaches `say`, clean the text with `printable` first, as `query.csv_cell` does: `say` strips control characters afterwards and would otherwise expose a formula hidden behind an escape character), and `commands.say` is the print backstop; never use a bare `print` for data in `commands.py` or `cli.py`. JSON output stays raw. A new renderer needs a case in `tests/test_output_safety.py`. `export --format json` follows the same split: its values are raw (`unifi_inventory.json`, git-ignored because it holds real MACs and IPs) while its CSV files go through `csv_safe`, and the two must stay the same data (`tests/test_export_json.py` compares them).
- Ignore rules (`settings.IgnoreRule`) match a finding's `code` exactly (case-sensitive, no wildcards) as well as `subject` (wildcards) and `message` (substring); all given fields must match and a rule needs at least one. A `code` must be in `settings.known_codes()` (`diagnose.CODES` plus `audit.AUDIT_CODES`; imported lazily because `diagnose` imports `settings`), otherwise loading fails with the valid codes listed. A new command that produces findings and applies ignore rules must add its codes to `known_codes`. A `Finding` built without a code never matches a code rule. An optional `until` date (a TOML date or a `YYYY-MM-DD` string, nothing else) is the last day a rule applies: `apply_ignores(findings, rules, today=None)` skips expired rules (tests pass `today`, or use dates far in the past or future), and `diagnose` and `audit` print one stderr warning per expired rule (`_warn_expired_rules`; never an exit code). The allowed keys are `code`, `subject`, `message`, `reason` and `until`.
- JSON documents: every `--json` output that is an object starts with `"version"` (a `JSON_VERSION` constant in its module, added where it is serialized, not in the in-memory structure) and has a JSON Schema in `docs/schemas/<name>.v1.schema.json` (draft 2020-12, objects left open so additive changes keep the version; `tests/test_json_schemas.py` validates every command's real output against a strict copy, so a key added without being declared fails, and compares the snapshot, diff and topology schemas with their `TypedDict`s). A new key goes in the code, the schema, the `TypedDict` if there is one and the changelog; removing or renaming a field, or changing its meaning, needs a new `version` and a new schema file. A new command with `--json` needs a schema and a line in `docs/schemas.md`. Plain lists (`query`, `new-clients`, `events`) stay bare arrays.
- `doctor` check ids (`config.env_file`, `endpoint.stat_alluser`...) are an interface like finding codes (`config.env_contents` reads the `.env` through `config.inspect_env_file`, names and line numbers only; a new variable the code reads goes in `config.KNOWN_VARIABLES`, which `tests/test_env_contents.py` pins against `example.env`): never renamed or reused, listed in `docs/configuration.md` (`tests/test_doctor.py` compares the two). A new read the commands depend on gets a `Reader` row (id, title, how to read it, whether every command needs it, what is lost without it). Nothing `doctor` prints may contain the API key, a notification URL, token or address, or the controller's host (`doctor.scrub` is the safety net; the messages themselves are fixed text). `UniFiAPIError` carries `kind` (`tls`, `unauthorized`, `forbidden`, `timeout`, `connection`, `request`, `http`, `bad_body`, `site`) and `status`: explain a failure with them, never by matching its message.
- Finding codes: every `Finding` built by a check in the `diagnose` package passes `code=` with a key of `diagnose.CODES` (`area.problem`, lower case). A code is an interface for `diagnose --json` and scripts: never rename or reuse one, add new ones to `CODES` and to the code table in `docs/diagnose.md`. `tests/test_diagnose_json.py` scans the source (a missing, unknown or unused code fails) and pins the list. The JSON document has a `version`; bump it only when a field is removed or renamed.
- HTTP (`client.py`): `_get` and `_post_system_log` share `_exchange`. A GET retries twice (connection error, timeout, 502/503/504; backoff `RETRY_BACKOFF_S`, which tests zero in `conftest.py`); the one POST is never retried; TLS, other statuses and bad bodies fail at once; 401 and 403 have their own messages; everything shown goes through `_redact`. `UNIFI_VERIFY_SSL` may be a CA bundle path (checked at config time), `UNIFI_TIMEOUT`/`--timeout` set the per-request limit, and the insecure-request warning is hidden per request with `warnings.catch_warnings`, never `urllib3.disable_warnings` (not thread-safe: parallel fetching must set a filter once).
- `--verbose`/`--debug` (global, before the command): `UniFiClient.debug` makes one DEBUG record per request attempt (label `METHOD path?params`, status or failure word, milliseconds; the POST label lists query keys only), counters feed `summary()`, and the `cli` log format prints each DEBUG record to stderr with a `[verbose]` prefix (`commands.verbose` is the same path); `UniFiClient.trace` stays as an optional extra sink for tests and callers. Trace text is built from the path, status and fixed words only: never from headers, bodies, exception text or query values, so it cannot carry the API key. Any new trace line must keep that property (`tests/test_verbose.py` checks it).
- Logging (`logs.py`, issue #177; `docs/logging.md`): diagnostics are records of a `logging.getLogger(__name__)` logger made with `logs.log_event(logger, level, EVENT, message, **fields)` (or `UniFiClient.debug`, `logs.warn`, `logs.verbose`), never a bare `print` or `sys.stderr.write`; command output stays on `say`. `EVENT` is a name from `logs.EVENTS` and a row of the table in `docs/logging.md` (never renamed or reused; `tests/test_logs.py` fails on an unlisted or an unused one). Every handler is made by `logs.configure` and carries `RedactFilter`: a new secret is added to `Config.secret_values` so `cli.main` registers it, a field named like a secret is hidden whatever its value, and INFO and above carry no client name, MAC or IP (identifiers only at DEBUG). The `cli` format is what the tool printed before logging existed (`Warning: ...`, `[verbose] ...`) and must stay byte-identical; a record that is neither a `warning` event nor an error shows there only when the level is below WARNING. Warnings go through `logs.warn` (`snapshot.warn` is the same function) so `logs.collect_warnings` can return them as data; a worker thread runs in a copy of the caller's context (`contextvars.copy_context().run`) so `request_id` reaches it. New settings: `LOG_LEVEL`, `LOG_FORMAT` (validated in `config.py`, listed in `tests/conftest.py`).
- Parallel reads (`snapshot.collect_snapshot`, `UniFiClient.parallel`): the independent reads of a collection run on a thread pool of `Config.parallel` workers (`UNIFI_PARALLEL_REQUESTS`, `--parallel`; `UniFiClient(workers=)` defaults to 1, so direct construction and the fake controller stay sequential unless a test asks). Each read appends its warnings to its own list and `_Reads.show_warnings` prints them in `_WARNING_ORDER`, so output does not depend on which request finished first; results are read back in a fixed order. The shared `requests.Session` is never mutated during a section, the counters and the trace are behind a lock, and the insecure-request warning is silenced once per section (`warnings.catch_warnings` is not thread-safe). New reads: add them to `_submit_extras`/`_apply_extras` and keep them free of shared mutable state. Indexes: code that handles every client builds `LocationIndex` / `AddressingIndex` once and reuses it (per-client rebuilds were quadratic; `tests/test_scale.py` guards the growth).
- Degradation policy: required data (devices, connected clients) fails the command; every legacy read is optional and warns, except `stat/alluser` for `new-clients` and `snapshot`/`diff`, which pass `users_required=True` because their output would be wrong without it.
- Raise `UniFiAPIError`/`ConfigError`; only `cli.main` turns them into messages and exit codes (it also turns an `OSError` from a file the command could not read or write into `ERROR: <reason> (<path>)` and exit 3, never a traceback; do not catch it yourself just to print).
- MACs are compared only through `util.normalize_mac` (upper case with colons, whatever separators the source used); never `(x or "").upper()` on a MAC, `tests/test_mac_formats.py` scans for it and re-spells every source's MACs across all commands. Likewise IPs through `normalize_ip`, and join records by id, never by a display name.
- Exit codes: 0 success, 1 and 2 are reserved for `diagnose` and `audit` findings (warning, critical; `audit` has no critical), 3 is a config/connection error, 4 is `client` finding no single match, 64 is a usage error. Do not reuse 1 or 2 for errors.
- The version is written once, as `homelab_probe.__version__`; `pyproject.toml` reads it (`dynamic = ["version"]` with `[tool.setuptools.dynamic]`), so bump it only there (`tests/test_accuracy.py` checks the wheel, `--version` and that nothing else repeats it). A PR changes `__version__` only when it is explicitly preparing a release or when the owner asks for a version bump; ordinary feature, fix, docs and dependency PRs add to `CHANGELOG.md` under `Unreleased` and leave the version alone. When asked to bump for a release, choose the next version from the unreleased changes: patch for bug fixes, docs that affect installed/released artifacts, dependency/security updates and small compatibility fixes; minor for new commands, flags, settings, output columns, checks, notification destinations, schemas or other user-visible capability; major only for a deliberate breaking change after owner approval (the project should normally stay `0.x` while the CLI and undocumented-controller behavior can still change). The README says only Network 10.6.106 was tested: do not widen that claim without testing.
- Dependencies are declared only in `pyproject.toml`; run `uv lock` after changing them and commit `uv.lock`.

## UniFi API notes

- Prefer the Integration API (`/proxy/network/integration/v1`): paginated, site IDs are UUIDs. `Config.site` may be a name, internal reference (`default`) or UUID; use `resolve_site`.
- Legacy `/proxy/network/api/s/{ref}/stat/...` takes the internal reference, not the UUID. It is used only for data the Integration API lacks (per-port counters, client-to-switch-port, DHCP reservations, network config).
- Legacy client records reference networks by legacy ids (from `rest/networkconf`), which do not match Integration API network UUIDs. A reservation is `use_fixedip` true; `fixed_ip` alone is stale-prone.
- Controller health is legacy `stat/health` (subsystems `wlan`, `lan`, `wan`, `www`, `vpn`). `lan`/`wlan` turn `error`/`warning` merely because devices are disconnected, so `diagnose` only trusts them when `num_disconnected` is 0. `Snapshot.health` is collected with `Needs(health=True)`.
- Overheating (`diagnose` `device.overheating`, checked on Network 10.6.106 with GETs only): legacy `stat/device` has an `overheating` bool on the gateway and 4 of 5 switches (all five present values were `false`; the sixth device and access points had no field, and the `true` case has never been seen live), so a missing or non-bool value is "unknown", never a finding, and only an online device is judged (an offline record keeps its last report). `has_temperature` is `false` on every device, including the gateway that lists `temperatures[]` (`{name, type, value}`), so it must not gate anything; the temperature limits depend on the model, so the numbers are not judged.
- Storage (`diagnose` `device.storage`, checked on Network 10.6.106 with GETs only): only the gateway's legacy `stat/device` record has `storage[]` (`{mount_point, name, size, type, used}`; two entries on the controller checked: eMMC `Backup` 6.6% used and `Temporary` 0.1%); the percentage is `used / size` so the unit never matters (the message cuts it to one decimal instead of rounding, so a warning never reads as the critical level), an entry with untrusted numbers (not numbers, `size` <= 0, `used` < 0 or above `size`) is skipped, and every entry is judged (noise goes in the ignore list). `stat/sysinfo` and `/api/system` have nothing about the controller application's own disk or database.
- Recent restarts (`diagnose` `device.recent_reboot`, checked on Network 10.6.106 with GETs only): legacy `stat/device` `uptime` (integer seconds; also `_uptime` and `startup_timestamp`) was on 8 of 10 devices on the controller checked (the two without it were probably the offline ones; not confirmed) and the shortest was 1.9 days, so a restart has never been seen live. The event log has no restart event key (18 distinct keys in 30 days, none about restarts), so only the current uptime is available, not a history. Information only; a firmware update restarts the device too and is not told apart.
- Switch port health comes from legacy `stat/device` `port_table`: `link_down_count` is cumulative since boot, drops must be judged as a percentage of packets, and `poe_good` is false on any PoE-capable port without a PoE device (do not use it). A device's `uplink` dict carries `speed`/`max_speed` for its own uplink port.
- Wi-Fi quality comes from legacy `stat/sta` (`signal` in dBm, `satisfaction`, `wifi_tx_retries_percentage`, `wifi_tx_attempts`, `radio` ng/na/6e) and each AP's `radio_table_stats` (`cu_total`, `tx_retries_pct`, `satisfaction`). Many clients lack these fields, radio `satisfaction` is -1 when unknown, and `anomalies` is on nearly every client (do not use it). Retry percentages need a minimum attempt count to mean anything.
- Neighboring networks (`wifi.py`): legacy `stat/rogueap` has one row per (BSSID, observing AP), so count distinct BSSIDs and keep the strongest signal; our own networks and APs never appear (still exclude `vap_table` BSSIDs and device MACs); there are no 6 GHz rows. Overlap is by frequency span (2.4 GHz channels are 5 MHz apart but ~22 MHz wide; 5/6 GHz widths occupy channel blocks), not by channel number. A radio's real channel is `radio_table_stats.channel`, not the configured `auto`. Neighbor SSIDs are other people's: show them (owner's decision) but only synthetic names in docs, tests and PRs.
- Internet health (`wan.py`): the `wan` health entry has `uptime_stats.WAN` (24h `availability`, `latency_average`, `monitors` and `alerting_monitors`); `alerting_monitors` lists monitors configured to alert, not failing ones (all read 100% when healthy), so judge each monitor by its own availability. The gateway's `wan1`/`wan2` dicts have link speed, `max_speed` and live `tx_bytes-r`/`rx_bytes-r` (bytes per second). Speedtest history is a GET: `v2/api/site/{ref}/speedtest` (`Snapshot.speedtests`, oldest first). `stat/report/*` returns only ids over GET (the data needs a POST, which is not approved), so do not build on it.
- NAT in front of the gateway (`wan.nat_status`): classified from the `wan_ip` of the `wan` health entry only (primary WAN, no outside lookup, no new endpoint). Ranges are listed explicitly (RFC 1918, 100.64.0.0/10, 169.254.0.0/16, IPv6 `fc00::/7` and `fe80::/10`) because Python's `is_private` also covers the documentation ranges the synthetic fixture uses (192.0.2.x, 203.0.113.x, 2001:db8::), which must count as public. A public address does not prove there is no NAT (a modem in front can hand the gateway a public one); say so rather than claiming a clean bill of health.
- Firewall (`firewall.py`, `Needs(firewall=True)`, checked on Network 10.6.106, which uses the **zone-based** firewall; spiked with GETs only): policies are legacy v2 `firewall-policies` (a bare list; 141 records of which 125 are `predefined` built-ins; `source`/`destination` each have `zone_id`, `matching_target` of `ANY`/`NETWORK`/`IP` (and others), `network_ids`, `ips`, `port_matching_type`/`port` and `match_opposite_*`; `protocol` is `all`/`tcp`/`udp`/`tcp_udp`/`icmpv6`; `hits` only when used), zones are v2 `firewall/zone` (`zone_key` is set on the six built-in zones and null on yours; `network_ids` are the legacy `rest/networkconf` `_id`s) and the matrix is v2 `firewall/zone-matrix` (a row's `_id` is the source zone, each `data[]._id` the destination zone, `action` of `allow_all`/`block_all`/`return_traffic` or null for custom rules, `policy_count` equals the policies for that pair). A user rule whose network was deleted keeps `matching_target` `NETWORK` with an **empty** `network_ids` (seen on disabled rules only; the finding words it as "probably deleted"). The Integration API (`firewall/policies`, `firewall/zones`) answers too but lists 25 policies, no ports or hit counts, and its user-defined policies have no `id`, so it is not used. Classic `rest/firewallrule`, `rest/firewallgroup` and `rest/portforward` and v2 `nat` answered with **no records** there, so port forward fields (`name`, `enabled`, `proto`, `dst_port`, `fwd`, `fwd_port`, `pfwd_interface`, `src`) are the legacy ones and unverified, and the classic firewall is deliberately not shown. Do not add a classic reader without real data to check it against.
- Audit (`audit.py`, `Needs(wlans=True, offline=True)`, checked on Network 10.6.106; spiked with GETs only): Wi-Fi networks are legacy `rest/wlanconf` (one record per SSID with `enabled`, `security` of `wpapsk` seen live and `open`/`wep` by the legacy API's convention, `wpa_mode`, `wpa3_support`/`wpa3_transition` (WPA2/WPA3 mixed has both true), `is_guest`, `l2_isolation` (client isolation), `hide_ssid`, `networkconf_id`; it also holds the passphrase in `x_passphrase`, which must never be read or printed). The Integration API `wifi/broadcasts` has `securityConfiguration.type`, `hideName` and `clientIsolationEnabled` but no guest flag, so it is not used. `rest/portconf` had no records, and a port's `native_networkconf_id` against a wired client's `network_id` differs for legitimate reasons on trunk ports (`forward` `all`/`customize` with `tagged_vlan_mgmt` `auto`): 7 of 7 observed mismatches were trunks, so that check was dropped; do not revive it without access-port (`forward` `native`) examples. Findings use the `Finding` of `diagnose` with their own `audit.*` codes in `audit.AUDIT_CODES` (not in `diagnose.CODES`).
- A `CLIENT_IP_CONFLICT` event names the devices in `parameters["CLIENTS"]["clients"]` (a list inside the object, each with `name`, `hostname`, `mac`, `ip`; the `ip` shown can differ from the conflicting address) and the network in `parameters["NETWORK"]`; connect/disconnect events use a single `CLIENT` instead. Merge devices across events by MAC and skip malformed entries.
- Partial `diagnose` runs and notifications: `notify.plan`/`baseline` take the `areas` that ran; a state entry whose code belongs to a skipped area is carried over untouched and never reported recovered (an entry with a code in no area counts as checked). Do not call `plan` for a partial run without `areas`.
- Event checks in `diagnose` read `snap.events` (collected with `Needs(events=EventQuery(...))`, window in `snap.event_window_seconds`); roaming is normal for phones, so it is info only. Use the snapshot's device names in findings so ignore rules match.
- The `client` view lists the client's events (matched by MAC, never by name) from `snap.events`, plus device-state events (`category == "UNIFI_DEVICES"`, no CLIENT parameter) for the devices on its path; internet-latency events also name the gateway but are not shown. `Snapshot.events_available` tells "log unreadable" from "no events".
- Event log: POST `/proxy/network/v2/api/site/{ref}/system-log/all` with `timestampFrom`/`timestampTo` (ms), `pageNumber`, `pageSize` and the server filters `categories`, `severities`, `keys`, `searchText`. Singular names (`category`, `severity`, `types`) are silently ignored, so test a filter by checking the total changes. Records are newest first with `{PLACEHOLDER}` messages filled from `parameters[X].name`; some audit events leave placeholders unresolved. Reading does not change event status.
- Uplinks: a device's legacy `uplink` dict has `uplink_mac` (the parent), `uplink_remote_port` (the PARENT's port), `port_idx` (its own uplink port), `speed` and `max_speed`; a gateway's uplink is its WAN link, not part of the tree. Integration `uplink.deviceId` names the parent when the legacy data does not. An offline device keeps its last known uplink. `DeviceIndex` (client_view.py) and `diagnose.uplink_speeds` are the shared helpers for names, state and negotiated-vs-capability speed.
- Saved snapshots (`history.py`, schema version 1) hold real MACs/IPs: they are written owner-only into the git-ignored `snapshots/`, and tests and docs use only the synthetic fixture. Match by MAC; keep constantly changing values (uptime, last-seen, traffic) out of the record; an unknown location is never a "move". They are kept per site: `snapshots/<util.site_key(site id)>/` (the resolved site UUID, from the snapshot's `site.id`, or `diagnose_document(...).meta["site"]` for the notification state), `--dir`/`--notify-state` are used as given, `history.site_snapshots` also lists the older files saved straight into `snapshots/` whose own record names the site (never moved), `diff` without `--dir` asks the controller which site is meant (`client.resolve_site`) only when it has to look for a snapshot, and the state file records `site` (another site's state is refused; the shared `snapshots/notify-state.json` is read for the site whose reference is `default` while it has no file of its own, and never changed). Snapshot file names are UTC (`snapshot-YYYYMMDD-HHMMSSZ[-N].json`; older local-time names without the `Z` are still read) and sort by instant then numeric suffix, never as text; `captured_at` inside the file keeps the local time with its offset.
- DHCP pools (`reservations.dhcp_pool`, checked against Network 10.6.106): `rest/networkconf` has `dhcpd_enabled` (bool, true on `corporate` networks and absent on `wan` and `remote-user-vpn` ones), `dhcpd_start`/`dhcpd_stop` (IP strings, ordered, inside the subnet) and `dhcp_relay_enabled` (false when the gateway serves DHCP); there is no `dhcpd_mode`. A VPN network has a start/stop without `dhcpd_enabled`, so require `dhcpd_enabled is True` and never key off the range alone. `ip_subnet` is the gateway address with a prefix (parse with `strict=False`).
- Offline reservations (`reservations.offline_reservations`): a reservation is offline when its MAC is in neither `snap.clients` nor `snap.devices`; its age is `now - last_seen` from `stat/alluser` (epoch seconds; missing, zero or non-numeric means never seen, a future value is clock skew and counts as 0). `diagnose` and `query reservations --offline` share that function so the listing is exactly what the check reports. The fixture's `last_seen_age_s` is converted to a real timestamp by `FakeSession`, so tests that need a fixed clock pass `now`.
- Randomized MACs (`util.is_randomized_mac`): locally administered unicast means `first_octet & 0x03 == 0x02` (second hex digit 2, 6, A or E); an address with the multicast bit set is never a client, so it is not flagged (the synthetic fixture's `bb:` addresses have both bits set and are therefore not randomized). It is a hint: VMs, containers and bridges use these too. Shown as `Private MAC` in `query clients` and `new-clients` (not in the CSV export), `identity.private_mac` in `client --json`, and two info findings in `diagnose`.
- Networks and Wi-Fi networks (`query networks`, `query wlans`, `query clients --network/--ssid/--ap`; `Needs(networks=True)` reads `rest/networkconf` alone; checked on Network 10.6.106 with GETs only): `rest/networkconf` has `purpose` (`corporate`, `wan`, `remote-user-vpn`); `vlan_enabled` and `vlan` only on the corporate ones and `ip_subnet` not on a WAN network, so a blank VLAN means "not said", not VLAN 1. `rest/wlanconf` has `wlan_bands` (a list of `2g`/`5g`/`6g`), `wpa_mode`, `wpa3_support` and `wpa3_transition` (WPA2/WPA3 mixed has both true, WPA3 only `wpa3_support`) and a `networkconf_id` that always resolved; its `x_passphrase` is in the same record and must never be read (`wlan_rows` reads named fields only, and a test makes the record raise on any other). `stat/sta` records carry `network_id` (resolved for every client, and the client's `network` text was the resolved name), and `wlanconf_id`, which also appears on clients that are not wired but have no `essid`, `ap_mac`, `radio` or `signal` at all (14 of 62 "wireless" clients on the controller checked): a client is on an SSID only when it has an `essid`, then its `wlanconf_id` (or, with no id, the `essid` text) says which network. Client counts are blank, not 0, when `stat/sta` could not be read; an unreadable `rest/networkconf` or `rest/wlanconf` stops `query networks`/`query wlans` with exit code 3 rather than printing an empty table.
- Client group membership is `network_members_group_ids` on legacy client records; group names/ids come from legacy v2 `/proxy/network/v2/api/site/{ref}/network-members-groups` (`client.legacy_v2`).
- Integration API and legacy fields were checked against one live controller (Network 10.6.106). Other versions and hardware may differ, and some fields vary by model (e.g. `mac_table_count` is null on some switches). Verify a new field against real data before relying on it.

## Safety

- Read-only: GET requests only, with **one approved exception**: the event log (`v2/system-log/all`) is POST-only, so `UniFiClient.system_log` sends a read-only query there (approved by the owner for event history, issue #49). It is used by `events` and, by default, by `diagnose` and `client` (`--no-events` skips it); a new feature may reuse it through the snapshot (`Needs(events=...)`) but must not add another POST. It is the only POST: do not add a general POST/PUT/PATCH/DELETE to `UniFiClient`, and do not point `system_log` at any other path. `tests/test_events.py` enforces this. Any other write to the controller needs explicit approval for that specific action.
- Notifications (`notify.py`, issue #85) are the **one outbound channel to anything other than the controller**, approved by the owner for ntfy, a generic webhook and email over SMTP (issue #107, approved 2026-10-02: one plain-text message per run, a provider with an app password, plain SMTP only with the lab opt-in and never with a password) and nothing else (no Slack/Discord adapters or other services without new approval). Rules: opt-in only (`diagnose --notify` and a configured destination; never on by default); the destination URL, token and mail account (host, user, password, addresses) are secrets from the environment, never printed, logged or put in an error (messages carry only the destination kind and a fixed reason; email failures map to fixed phrases in `notify._email_failure`, never the library's text, and the exception order there matters because `SMTPException` and `ssl.SSLError` are `OSError`s); content is limited to the finding identity, severity and text, never the API key, controller address or site id, and `--notify-redact` removes names, addresses and MACs; HTTPS only, TLS verified, redirects not followed; email is STARTTLS or implicit TLS with `ssl.create_default_context()` (never an unverified context, and a password is refused over plain SMTP both in `config.validate_smtp` and in `notify._send_email`); a half-set `NOTIFY_SMTP_*`/`NOTIFY_EMAIL_*` configuration is an error, never a silent no-op; state is owner-only in the git-ignored `snapshots/`. `notify.py` must not import or call `UniFiClient`, and `tests/test_notify.py` enforces that and that it has one `requests.post`, and `tests/test_notify_email.py` that `notify.py` is the only module that imports `smtplib`. It must never write to the controller.
- Contacting the real controller: read-only GET checks (and the approved event-log POST) are fine once the task is approved; summarize or mask what they return and never paste it into the repo. Any other request, anything that changes the controller, and anything that sends data elsewhere needs explicit approval for that specific action. If a feature needs an endpoint nobody has probed yet, say so and get a go-ahead for the GET spike first.
- Never print or commit `.env` or the API key. Redact real MACs, IPs and hostnames in issues, commits, PRs and test fixtures.

## Testing

- Tests are hermetic: an autouse fixture in `tests/conftest.py` runs every test in an empty working directory with `UNIFI_URL`, `UNIFI_API_KEY`, `UNIFI_SITE_ID`, `UNIFI_VERIFY_SSL` and `HLP_ENV` unset, because `.env` and `hlp.toml` are read from the current directory. Never rely on, or patch around, the developer's real files; a test that needs a file creates it in the working directory or changes directory itself.
- Golden files and docs drift: command output is pinned in `tests/golden/*.txt` (`tests/test_golden.py`, normalised so times and padding do not matter) and the sample blocks in the README and `docs/` must equal it (`tests/test_docs_drift.py`, which also checks that every example in them parses, every command has a Commands row in the README and every long option is mentioned in the README or a docs page; `tests/test_docs_layout.py` keeps the README short and every link and old anchor valid). When you change an output on purpose: `UPDATE_GOLDEN=1 uv run pytest tests/test_golden.py`, then `UPDATE_README_SAMPLES=1 uv run pytest tests/test_docs_drift.py`, and review both diffs. A new command or flag needs its README row and a mention in its docs page, or the suite fails. `tests/test_entry_points.py` and `tests/test_exit_codes.py` cover the launcher, the console script and every documented exit code. Line and branch coverage is 100% and CI enforces it (the `Coverage (100%)` job runs `uv run coverage run -m pytest` and `uv run coverage report`, configured in `pyproject.toml`; a gap fails the pull request): keep it, justify any `pragma: no cover` with a comment, and make a test independent of the Python version that runs it (the TOML reader's errors differ between versions: test with stand-ins). Tests that need `fish` or util-linux `flock` skip where they are missing (a Mac), the cron tests use a stand-in `flock`, so the Coverage job, which installs fish and zsh, is where everything runs; `tests/test_coverage_config.py` pins the job and the settings.
- Demo mode (`--demo`, issue #175; `homelab_probe/demo/`, `cli.main`): `--demo` never calls `load_config`, so no `.env`, environment variable, `HLP_ENV` or notification destination can reach a demo; the settings file is used only when `--config` names one (otherwise `DiagnoseSettings()` defaults, never `./hlp.toml`); the client's session is a `DemoSession` and the address is `.invalid`. `_check_demo` refuses (exit 64) `--env-file`, `doctor`, `snapshot`, `diff` and every `--notify*` flag: a new command that reads or writes the user's own files or sends anything must be added to `DEMO_REFUSED` (or the notify check). Demo output says `Demo mode: ...` on stderr only. `tests/test_demo.py` runs every command with the network, the sockets, `load_config` and `load_dotenv` made to fail. The fixture is `homelab_probe/demo/controller.json` and ships in the wheel (`package-data`).
- `FakeSession` (`DemoSession`) deep-copies the fixture for each test, so tests may mutate the data they get; keep it that way.
- Tests use the synthetic fixture `homelab_probe/demo/controller.json` served by `FakeSession` in `tests/conftest.py`; never hit the live controller from tests, except the opt-in `live` tests below. Add tests for new features and extend the fixture rather than pasting real data (redact MACs, IPs, names).
- The contract (`tests/contract.py`) lists, per endpoint, the fields the code reads: `always` (in every record), `somewhere` (in at least one record of a normal site) and `optional` (only some models, versions or events). Three checks hang on it: `tests/test_contract_fixture.py` fails when the fixture lacks a listed field, when the code reads a field that is not listed (it runs every command through `tests/field_tracking.py` and records each key touched) and when a listed field is never read. So when you read a new field: list it in the contract, then add it to the fixture (and its golden files and the samples in the docs if the output changes). Do not weaken a tier to make a test pass without knowing why the field can be missing.
- Live contract tests: `uv run pytest -m live` (`tests/test_live_contract.py`) reads the real controller once and checks every endpoint against the contract. They are deselected by default (`addopts` in `pyproject.toml`) and in CI, use the real `.env` (the isolation fixture steps aside for tests marked `live`), make GET requests and the one approved event log query (`RecordingSession` raises on anything else) and print endpoint and field names, never values. **They contact the real controller, so ask before running them** (like any other command that does).
- `tools/record_fixture.py` records the controller into `tools/recorded/controller.json` (git-ignored, owner-only) in the shape of the test fixture, keeping only contract fields and passing everything through `tools/sanitize.py`: MACs, addresses, ids, names, SSIDs and the ISP become synthetic values, consistently and deterministically, and `check_no_leaks` refuses to write anything that still holds a real value or an address it did not issue. It also contacts the controller: ask first, and read only its counts and field names; never paste a recording into an issue, a PR or the tests. Change the sanitiser only with tests in `tests/test_sanitize.py` (the leak check must keep rejecting an unmapped address).

## Before opening a PR: review your own diff

Copilot reviews every PR and keeps finding the same kinds of defect (about 15 PRs read: #61 to #119). Look for these in your own diff first, and fix them before pushing; each was a real finding.

1. **Acceptance criteria.** Re-read the issue and list every requirement with the test that proves it in the PR description. A requirement that is not in a test is usually the one that was missed (#73: the controller version in the contract report).
2. **A claim is a test.** Words like "never", "only", "every", "reads less", "no extra requests", "redacted" must be attacked, not assumed: count the requests, poison a value, grep every output path (stdout, stderr, `--verbose`, JSON, errors). Redaction and "never printed" failed at three separate emission points (#98); the recorder's "only contract fields reach disk" failed on an early return (#118); "reads only what it needs" still read every device (#106).
3. **Sibling paths.** When you add behavior to one collector, command, renderer or loader, search for its siblings and apply it or say why not (`collect_event_snapshot` next to `collect_snapshot`, text next to JSON, one command next to the others).
4. **Data edge cases** for every new key, join, dedup, comparison or threshold: missing, empty, `None`, duplicate, a different spelling of the same thing (MAC and IP forms), a display name used as a key (use the id), a non-string, special-use addresses, a limit. An "all traffic" or "every X" condition must check every dimension (ports on both sides, not only the destination). Two records with the same missing field are not duplicates.
5. **Partial failure.** For each optional read that can fail, state what the output then claims and check the rest still works exactly as the warning says (zone names unavailable must not hide every policy). A warning must describe the real impact, not the nearest one.
6. **Mechanical conventions:** a new environment variable goes in `tests/conftest.py` `CONFIG_VARIABLES` (a test enforces it); a new renderer gets a case in `tests/test_output_safety.py`; a new message built from a response or exception goes through `_redact`; no raw exception text on a terminal where a response body can be in it; after moving or splitting code, fix the comments, docstrings and documentation text that still describe the old place ("this module"); tests are exempt from E501 but source is not; a test that needs an invisible or direction-changing character writes it as an escape (`tests/test_no_hidden_characters.py` fails on a raw one).
7. **Tests must be able to fail.** After writing a test, break the thing it guards (remove the field, revert the fix) and watch it fail. No silently skipped parametrizations (a missing console script must fail the collection, not shrink it), no parameter that only appears in the failure message, and a completeness check must force the fallback branches it claims to cover, not only the main ones.
8. **Docs run.** Paste each shell snippet and example you wrote; an example must do what its sentence says (an ignore rule that silences one finding but not the other), catalogue strings must be whole sentences, and every new range or option has to be listed everywhere it applies (IPv6 next to IPv4).
9. **Last read.** Read `git diff main` once as a skeptical reviewer: for every changed line ask what input breaks it and which test would notice.

## Releases

- The owner cuts releases; never create a tag or a GitHub release from here, and do not push a `v*` tag (the release workflow publishes on it). Prepare the pull request, say what remains, and stop.
- Do not bump `homelab_probe.__version__` in every PR. Most PRs keep the current version and only add their notes under `CHANGELOG.md` `Unreleased`; the version moves in a dedicated release-prep PR, or in another PR only when the owner explicitly asks.
- **Tell the owner when a release is due; do not wait to be asked, and never do it yourself.** At the end of a task (after a PR merges, or when asked what is next), look once at whether a release makes sense and, if it does, say so in a couple of lines: the version you would pick and why (by the bump rules above), what is in `Unreleased`, and that the next step is a release-prep PR followed by the owner's tag. Then continue with what was asked. Check with `git tag --list 'v*'` and `git log <latest tag>..main --oneline` (before the first tag, everything under `Unreleased` counts), the `CHANGELOG.md` `Unreleased` entry, `gh run list --branch main --limit 3` and `gh pr list`. Raise it when **all** of these hold: `main` has user-visible changes that no tag contains; the latest CI run on `main` passed; no open PR is half of a feature that belongs in the same release (a command whose second PR is still open, or a change waiting on review that the changelog already mentions); and either (a) it is a **security fix, a bug fix people would notice, or a change to an exit code, finding code or JSON `version`**, which is worth releasing soon on its own (a patch, or a minor if the change is breaking), or (b) a **coherent batch is finished**: the issues being worked on together are merged and nothing is left in progress, which is usually a new command, flag, check or setting (a minor). Do not raise it for docs-only, test-only or CI-only changes, for a change that is not merged yet, after every PR, or again in the same session once the owner has said "not yet"; ask again only when something new qualifies. If the owner says yes, prepare the release-prep PR as described below and stop at the PR.
- Follow [MAINTAINING.md](MAINTAINING.md#prepare-a-release) for the release-prep PR and [Tag and Publish](MAINTAINING.md#tag-and-publish) for the owner's tagging steps and automated release behavior. Keep those procedures current in that file rather than duplicating them here. `tests/test_changelog.py` pins the release workflow's validation and publishing rules.
- The first release is 0.2.0 (the owner chose it over 0.1.0 and 1.0.0): still 0.x because the endpoints are undocumented, only Network 10.6.106 was tested and the command line may still change.

## Git and GitHub

- Commit only when asked. When asked to check in code, always create a feature branch and open a PR; never commit to `main`.
- Open the PR and stop; do not merge it. PRs normally wait for a GitHub Copilot code review, and the user merges after addressing it. Merge only when the user explicitly asks for that PR.
- This repo is a fork, so always pass `--repo jeffholst/homelab-probe` to `gh pr create`; the default target is the upstream repo.
- Keep local branches clean. Never work on `main`; it only moves via `git pull`. Start each branch from an up-to-date `main` unless the work depends on an open PR. Keep the PR branch (and stay on it) while the PR is open, since review fixes are pushed to it.
- After a PR is merged, clean up: `git checkout main && git pull`, then `git branch -d <branch>` (`-d` refuses if unmerged, so it doubles as a check; use `-D` only after confirming the PR is merged, e.g. after a squash merge). `fetch.prune` is enabled globally and the repo deletes head branches on merge, so `origin/*` refs clean themselves up. Before finishing a task, check `git branch -vv` and delete any local branch whose PR is merged; leave branches with open PRs alone.
- Dependabot (`.github/dependabot.yml`: the GitHub Actions and `uv.lock`, weekly, one grouped PR per ecosystem) opens PRs like any other: nothing merges until the owner asks, CI must be green (tests on Python 3.10 to 3.13, ruff, mypy, `uv lock --check`), and a bump that changes `uv.lock` is reviewed for its changelog and for new transitive dependencies. Keep actions pinned to exact tags (`astral-sh/setup-uv` publishes no floating `v10`; `tests/test_dependabot_config.py` enforces it). Dependabot alerts and security updates are repository settings only the owner can switch on (Settings, Advanced Security); do not try to do it from here.

# UniFi Sentinel

Fork of [ericfitz/unifi-clients-export](https://github.com/ericfitz/unifi-clients-export), being extended into a tool for querying, troubleshooting and inventorying a UniFi Network controller. Keep the Apache-2.0 license and upstream credit.

## Layout

- `unifi-sentinel.py`: thin launcher; all logic lives in `unifi_sentinel/`.
- `unifi_sentinel/config.py`: env/`.env` loading. `client.py`: `UniFiClient`, the only place that makes HTTP calls. `snapshot.py`: `collect_snapshot(client, site, Needs(...))`, the one read of the controller; a command declares what it reads with a `Needs` (and an `EventQuery` for the event log), never with loose flags. `export.py`, `query.py`, `reservations.py`, `new_clients.py`, `client_view.py`, `events.py`, `wan.py`, `firewall.py`, `audit.py`, `wifi.py`, `topology.py`, `history.py` and the `diagnose/` package: pure functions over a `Snapshot`. `diagnose/` has one module per topic (`devices`, `health`, `addresses`, `reserved`, `ports`, `wireless`, `event_checks`, plus `model` for severities, codes and `Finding`, `output`, and `areas`); a new check is a function in the module of its topic, a code in `model.CODES`, and one line in `areas.CHECKS` with every area it can emit (the order there is part of the output). `areas.py` maps code prefixes to the areas of `diagnose --only/--skip` (`devices`, `health`, `wan`, `clients`, `reservations`, `ports`, `wifi`, `events`) and `needs_for` says what a selection reads: a new code needs its prefix in `AREAS`, and a check that starts using new snapshot data must be reflected in `needs_for` (`tests/test_diagnose_areas.py` runs every area on the minimal reads and compares with the full run, so a missing read fails). `util.py`: shared helpers: output safety (`printable`, `clean_data`, `safe_output`, `csv_safe`) and small value helpers (`number`, `number_or_zero`, `known_percent`, `plural`, `normalize_mac`, `hex_digits`, `epoch_text`, `format_time`, `search_rows`, `is_randomized_mac`, `describe_age`). `notify.py`: notifications (plan what changed, wording, the one outbound `requests.post`, state file). `watch.py`: `diagnose --watch` (what changed since the last pass, from `notify.plan` with an in-memory state; the loop and its injectable `commands.WATCH_SLEEP` are in `commands.py`; never combined with `--json` or `--notify`, and it must not write or send anything). `settings.py`: `diagnose` thresholds and ignore rules from an optional TOML file; new checks take their thresholds from `DiagnoseSettings`, never module constants. `cli.py`: the argument parser and `main` (config, client, then the command's handler). `commands.py`: one section per subcommand (its arguments, its checks, its handler, the `Needs` it declares) and the `COMMANDS` registry.
- `tools/`: development scripts that are not part of the package: `record_fixture.py` (records a real controller into a sanitised fixture) and `sanitize.py` (the deterministic sanitiser and its leak check). `tests/contract.py` is the one table of the fields the code reads from each endpoint (also the request guard `RecordingSession` and `endpoint_of`); `tests/field_tracking.py` derives that list from what the code actually touches.
- New features are new subcommands: a section in `commands.py` (`_add_x` for the arguments, `_check_x` for combinations to reject, `_run_x(ctx) -> int` for the handler, which declares its `Needs`) plus one `Command(...)` row in `COMMANDS`, backed by modules that take a `Snapshot`; keep fetching (snapshot), analysis and output separate.
- Shell completion (`completion.py`): the bash, zsh and fish scripts are generated from the argument parser, so a new option needs nothing and a value argparse cannot express goes in `VALUE_HINTS`; `unifi-sentinel completion SHELL` is the command that runs through `Command.run_local`, before any `.env` is read, so it works on a machine with no configuration. `tests/test_completion.py` runs the bash script in a real bash and checks that every command and option is in every script.

## Commands

- Run: `uv run unifi-sentinel.py <export|query|client|new-clients|diagnose|events|wan|firewall|audit|wifi|topology|snapshot|diff|completion|info>`
- Tests: `uv run pytest`. Lint: `uv run ruff check .` (add `--fix` for import order and unused imports). Types: `uv run mypy` (clean, and blocking in CI: fix a finding with a real narrowing or type, not a `# type: ignore`, which `warn_unused_ignores` would also police). The shapes worth naming are `TypedDict`s: the saved snapshot (`history.SnapshotRecord` with `DeviceRecord`, `ClientRecord`, `ReservationRecord`; `Diff`/`DiffPart`/`Change`), the topology (`topology.Topology`, `Node`, `Summary`) and the Wi-Fi rows (`wifi.Radio`, `Neighbor`). Controller payloads (`Snapshot.devices`, `legacy_clients`, ...) stay `Dict[str, Any]` on purpose: they are undocumented and vary by model, so typing them would claim knowledge we do not have. A record that is read back from disk (`load_snapshot`) is validated first and then cast, because `isinstance` cannot check a `TypedDict`. When you add a key to one of these, add it to the TypedDict: `tests/test_typed_records.py` compares each TypedDict with the keys of a real capture, tree and radio/neighbor list (Python 3.10 has no `NotRequired`, so a key that exists only sometimes goes in a `total=False` subclass, as `Node` does); use `util.record_for` to look up a record by an id that may be missing. Lockfile: `uv lock --check`. CI (`.github/workflows/ci.yml`) runs all of these on every push to `main` and every PR, tests on Python 3.10 to 3.13; run `uv run pytest` and `uv run ruff check .` before pushing. The minimum Python is 3.10.

## Documentation

- **The README is the quickstart; the detail is in `docs/`.** Every new feature is documented in the same PR in both places: in `README.md` a row in the Commands table (with its `[details]` link), one usage example in the Usage block and, for a command, a one-line stub under the same heading as before with a link; in the `docs/` page of its group the section (columns, filters, data sources, caveats, sample output, the code table for new finding codes), the layout block of `docs/development.md` if you add a module, and a `--help`-accurate list of flags. The pages are `diagnose.md` (diagnose and audit), `notifications.md`, `scheduling.md` (cron, systemd, launchd and Docker: every snippet is run by `tests/test_docs_scheduling.py` or was run by hand, so change them together with the code they depend on, such as exit codes and the default state file), `inventory.md` (query, export, snapshot, diff, new-clients), `network.md` (topology, wifi, wan, firewall, events, client), `configuration.md` (settings, `--verbose`, troubleshooting), `examples.md`, `features.md` and `development.md`; a new page must be linked from the README. Keep the README under 250 lines (`tests/test_docs_layout.py`), never delete a heading without moving it (every anchor the README ever had must exist somewhere, so old links keep working) and use only relative links that resolve (the same test checks them). Changed behavior (flags, output columns, exit codes) updates the existing text too.
- `SECURITY.md`, `CONTRIBUTING.md` and `.github/ISSUE_TEMPLATE/` (two issue forms and `config.yml`) are the community files; `tests/test_community_files.py` checks their links, the form schema, that every example address is made up, and that the commands `CONTRIBUTING.md` lists are the ones CI runs. When a rule here changes (a command CI runs, the README ceiling, the Python floor, a label, the supported versions), change them too. Private vulnerability reporting is a repository setting only the owner can switch on (the `SECURITY.md` link needs it).
- Keep `CLAUDE.md` current when adding a module or subcommand (Layout, Commands) or learning something non-obvious about the API.
- Example output in docs must come from the synthetic fixture, never from a real network.
- Before opening a PR, check that the README and `docs/` match `unifi-sentinel <command> --help` (`tests/test_docs_drift.py` checks the options).
- Every user-visible change (a command, a flag, an output column, a check, a setting, a fix people would notice) gets a line in `CHANGELOG.md`, under the entry that is still marked `Unreleased` (after a release, open a new `## [Unreleased]` heading above the last one). A change to an exit code, a finding code or a JSON `version` must be called out; `tests/test_changelog.py` fails if a command or a finding code named there does not exist, or a command is missing from it.

## Conventions

- Reading the controller: a new read is a new field of `snapshot.Needs` plus the code that honors it, and every command passes the smallest `Needs` it uses (`tests/test_needs.py` pins which endpoints each command reads, so a command that starts reading more fails the suite until its declaration and the test agree). Required data (`users_required`) fails the command; everything else degrades with a warning.
- Shared helpers live in `util.py` and are imported; do not define a private copy of one in a module (the same `_num` once existed in five places), and do not import another module's underscore-prefixed names. `tests/test_util_helpers.py` tests them directly.
- Stdlib `csv`, not pandas. Match the surrounding style; type-hint public functions.
- Configuration (`config.py`): the `.env` file comes from `--env-file`, then `UNIFI_SENTINEL_ENV`, then `./.env` in the current directory only (never the package directory or parent directories). Validate every setting (`VERIFY_SSL` words, `SITE_ID` characters (and `--site`, which beats `SITE_ID` and goes through the same `validate_site`, naming the option in its messages), `CONTROLLER_URL` scheme and host, `http://` only with `ALLOW_INSECURE_HTTP`) and percent-encode site references in URL paths. The API key is never printed: `Config.api_key` is `repr=False`, `UniFiClient._redact` strips it from response bodies and exception text, and a loose-permission `.env` gives a warning (`Config.warnings`, printed by `cli.main`), never an error. Any new message built from a response or an exception goes through `_redact`.
- Output safety (`util.py`): names (clients, devices, SSIDs, event text) are untrusted. Text renderers call `clean_data` on their report (or `printable` on single values; `format_table` cleans every cell), every CSV cell goes through `csv_safe` (for output that reaches `say`, clean the text with `printable` first, as `query.csv_cell` does: `say` strips control characters afterwards and would otherwise expose a formula hidden behind an escape character), and `commands.say` is the print backstop; never use a bare `print` for data in `commands.py` or `cli.py`. JSON output stays raw. A new renderer needs a case in `tests/test_output_safety.py`.
- Ignore rules (`settings.IgnoreRule`) match a finding's `code` exactly (case-sensitive, no wildcards) as well as `subject` (wildcards) and `message` (substring); all given fields must match and a rule needs at least one. A `code` must be in `settings.known_codes()` (`diagnose.CODES` plus `audit.AUDIT_CODES`; imported lazily because `diagnose` imports `settings`), otherwise loading fails with the valid codes listed. A new command that produces findings and applies ignore rules must add its codes to `known_codes`. A `Finding` built without a code never matches a code rule. An optional `until` date (a TOML date or a `YYYY-MM-DD` string, nothing else) is the last day a rule applies: `apply_ignores(findings, rules, today=None)` skips expired rules (tests pass `today`, or use dates far in the past or future), and `diagnose` and `audit` print one stderr warning per expired rule (`_warn_expired_rules`; never an exit code). The allowed keys are `code`, `subject`, `message`, `reason` and `until`.
- JSON documents: every `--json` output that is an object starts with `"version"` (a `JSON_VERSION` constant in its module, added where it is serialized, not in the in-memory structure) and has a JSON Schema in `docs/schemas/<name>.v1.schema.json` (draft 2020-12, objects left open so additive changes keep the version; `tests/test_json_schemas.py` validates every command's real output against a strict copy, so a key added without being declared fails, and compares the snapshot, diff and topology schemas with their `TypedDict`s). A new key goes in the code, the schema, the `TypedDict` if there is one and the changelog; removing or renaming a field, or changing its meaning, needs a new `version` and a new schema file. A new command with `--json` needs a schema and a line in `docs/schemas.md`. Plain lists (`query`, `new-clients`, `events`) stay bare arrays.
- Finding codes: every `Finding` built by a check in the `diagnose` package passes `code=` with a key of `diagnose.CODES` (`area.problem`, lower case). A code is an interface for `diagnose --json` and scripts: never rename or reuse one, add new ones to `CODES` and to the code table in `docs/diagnose.md`. `tests/test_diagnose_json.py` scans the source (a missing, unknown or unused code fails) and pins the list. The JSON document has a `version`; bump it only when a field is removed or renamed.
- HTTP (`client.py`): `_get` and `_post_system_log` share `_exchange`. A GET retries twice (connection error, timeout, 502/503/504; backoff `RETRY_BACKOFF_S`, which tests zero in `conftest.py`); the one POST is never retried; TLS, other statuses and bad bodies fail at once; 401 and 403 have their own messages; everything shown goes through `_redact`. `VERIFY_SSL` may be a CA bundle path (checked at config time), `TIMEOUT`/`--timeout` set the per-request limit, and the insecure-request warning is hidden per request with `warnings.catch_warnings`, never `urllib3.disable_warnings` (not thread-safe: parallel fetching must set a filter once).
- `--verbose`/`--debug` (global, before the command): `UniFiClient.trace` receives one line per request attempt (label `METHOD path?params`, status or failure word, milliseconds; the POST label lists query keys only), counters feed `summary()`, and `cli.main` prints them to stderr with a `[verbose]` prefix (`commands.verbose`). Trace text is built from the path, status and fixed words only: never from headers, bodies, exception text or query values, so it cannot carry the API key. Any new trace line must keep that property (`tests/test_verbose.py` checks it).
- Parallel reads (`snapshot.collect_snapshot`, `UniFiClient.parallel`): the independent reads of a collection run on a thread pool of `Config.parallel` workers (`PARALLEL_REQUESTS`, `--parallel`; `UniFiClient(workers=)` defaults to 1, so direct construction and the fake controller stay sequential unless a test asks). Each read appends its warnings to its own list and `_Reads.show_warnings` prints them in `_WARNING_ORDER`, so output does not depend on which request finished first; results are read back in a fixed order. The shared `requests.Session` is never mutated during a section, the counters and the trace are behind a lock, and the insecure-request warning is silenced once per section (`warnings.catch_warnings` is not thread-safe). New reads: add them to `_submit_extras`/`_apply_extras` and keep them free of shared mutable state. Indexes: code that handles every client builds `LocationIndex` / `AddressingIndex` once and reuses it (per-client rebuilds were quadratic; `tests/test_scale.py` guards the growth).
- Degradation policy: required data (devices, connected clients) fails the command; every legacy read is optional and warns, except `stat/alluser` for `new-clients` and `snapshot`/`diff`, which pass `users_required=True` because their output would be wrong without it.
- Raise `UniFiAPIError`/`ConfigError`; only `cli.main` turns them into messages and exit codes (it also turns an `OSError` from a file the command could not read or write into `ERROR: <reason> (<path>)` and exit 3, never a traceback; do not catch it yourself just to print).
- MACs are compared only through `util.normalize_mac` (upper case with colons, whatever separators the source used); never `(x or "").upper()` on a MAC, `tests/test_mac_formats.py` scans for it and re-spells every source's MACs across all commands. Likewise IPs through `normalize_ip`, and join records by id, never by a display name.
- Exit codes: 0 success, 1 and 2 are reserved for `diagnose` and `audit` findings (warning, critical; `audit` has no critical), 3 is a config/connection error, 4 is `client` finding no single match, 64 is a usage error. Do not reuse 1 or 2 for errors.
- The version is written once, as `unifi_sentinel.__version__`; `pyproject.toml` reads it (`dynamic = ["version"]` with `[tool.setuptools.dynamic]`), so bump it only there (`tests/test_accuracy.py` checks the wheel, `--version` and that nothing else repeats it). A PR changes `__version__` only when it is explicitly preparing a release or when the owner asks for a version bump; ordinary feature, fix, docs and dependency PRs add to `CHANGELOG.md` under `Unreleased` and leave the version alone. When asked to bump for a release, choose the next version from the unreleased changes: patch for bug fixes, docs that affect installed/released artifacts, dependency/security updates and small compatibility fixes; minor for new commands, flags, settings, output columns, checks, notification destinations, schemas or other user-visible capability; major only for a deliberate breaking change after owner approval (the project should normally stay `0.x` while the CLI and undocumented-controller behavior can still change). The README says only Network 10.6.106 was tested: do not widen that claim without testing.
- Dependencies are declared only in `pyproject.toml`; run `uv lock` after changing them and commit `uv.lock`.

## UniFi API notes

- Prefer the Integration API (`/proxy/network/integration/v1`): paginated, site IDs are UUIDs. `Config.site` may be a name, internal reference (`default`) or UUID; use `resolve_site`.
- Legacy `/proxy/network/api/s/{ref}/stat/...` takes the internal reference, not the UUID. It is used only for data the Integration API lacks (per-port counters, client-to-switch-port, DHCP reservations, network config).
- Legacy client records reference networks by legacy ids (from `rest/networkconf`), which do not match Integration API network UUIDs. A reservation is `use_fixedip` true; `fixed_ip` alone is stale-prone.
- Controller health is legacy `stat/health` (subsystems `wlan`, `lan`, `wan`, `www`, `vpn`). `lan`/`wlan` turn `error`/`warning` merely because devices are disconnected, so `diagnose` only trusts them when `num_disconnected` is 0. `Snapshot.health` is collected with `Needs(health=True)`.
- Overheating (`diagnose` `device.overheating`, checked on Network 10.6.106 with GETs only): legacy `stat/device` has an `overheating` bool on the gateway and most switches (`false` on all 6 checked; the `true` case has never been seen live) and not on access points, so a missing or non-bool value is "unknown", never a finding, and only an online device is judged (an offline record keeps its last report). `has_temperature` is `false` on every device, including the gateway that lists `temperatures[]` (`{name, type, value}`), so it must not gate anything; the temperature limits depend on the model, so the numbers are not judged.
- Switch port health comes from legacy `stat/device` `port_table`: `link_down_count` is cumulative since boot, drops must be judged as a percentage of packets, and `poe_good` is false on any PoE-capable port without a PoE device (do not use it). A device's `uplink` dict carries `speed`/`max_speed` for its own uplink port.
- Wi-Fi quality comes from legacy `stat/sta` (`signal` in dBm, `satisfaction`, `wifi_tx_retries_percentage`, `wifi_tx_attempts`, `radio` ng/na/6e) and each AP's `radio_table_stats` (`cu_total`, `tx_retries_pct`, `satisfaction`). Many clients lack these fields, radio `satisfaction` is -1 when unknown, and `anomalies` is on nearly every client (do not use it). Retry percentages need a minimum attempt count to mean anything.
- Neighboring networks (`wifi.py`): legacy `stat/rogueap` has one row per (BSSID, observing AP), so count distinct BSSIDs and keep the strongest signal; our own networks and APs never appear (still exclude `vap_table` BSSIDs and device MACs); there are no 6 GHz rows. Overlap is by frequency span (2.4 GHz channels are 5 MHz apart but ~22 MHz wide; 5/6 GHz widths occupy channel blocks), not by channel number. A radio's real channel is `radio_table_stats.channel`, not the configured `auto`. Neighbor SSIDs are other people's: show them (owner's decision) but only synthetic names in docs, tests and PRs.
- Internet health (`wan.py`): the `wan` health entry has `uptime_stats.WAN` (24h `availability`, `latency_average`, `monitors` and `alerting_monitors`); `alerting_monitors` lists monitors configured to alert, not failing ones (all read 100% when healthy), so judge each monitor by its own availability. The gateway's `wan1`/`wan2` dicts have link speed, `max_speed` and live `tx_bytes-r`/`rx_bytes-r` (bytes per second). Speedtest history is a GET: `v2/api/site/{ref}/speedtest` (`Snapshot.speedtests`, oldest first). `stat/report/*` returns only ids over GET (the data needs a POST, which is not approved), so do not build on it.
- NAT in front of the gateway (`wan.nat_status`): classified from the `wan_ip` of the `wan` health entry only (primary WAN, no outside lookup, no new endpoint). Ranges are listed explicitly (RFC 1918, 100.64.0.0/10, 169.254.0.0/16, IPv6 `fc00::/7` and `fe80::/10`) because Python's `is_private` also covers the documentation ranges the synthetic fixture uses (192.0.2.x, 203.0.113.x, 2001:db8::), which must count as public. A public address does not prove there is no NAT (a modem in front can hand the gateway a public one); say so rather than claiming a clean bill of health.
- Firewall (`firewall.py`, `Needs(firewall=True)`, checked on Network 10.6.106, which uses the **zone-based** firewall; spiked with GETs only): policies are legacy v2 `firewall-policies` (a bare list; 141 records of which 125 are `predefined` built-ins; `source`/`destination` each have `zone_id`, `matching_target` of `ANY`/`NETWORK`/`IP` (and others), `network_ids`, `ips`, `port_matching_type`/`port` and `match_opposite_*`; `protocol` is `all`/`tcp`/`udp`/`tcp_udp`/`icmpv6`; `hits` only when used), zones are v2 `firewall/zone` (`zone_key` is set on the six built-in zones and null on yours; `network_ids` are the legacy `rest/networkconf` `_id`s) and the matrix is v2 `firewall/zone-matrix` (a row's `_id` is the source zone, each `data[]._id` the destination zone, `action` of `allow_all`/`block_all`/`return_traffic` or null for custom rules, `policy_count` equals the policies for that pair). A user rule whose network was deleted keeps `matching_target` `NETWORK` with an **empty** `network_ids` (seen on disabled rules only; the finding words it as "probably deleted"). The Integration API (`firewall/policies`, `firewall/zones`) answers too but lists 25 policies, no ports or hit counts, and its user-defined policies have no `id`, so it is not used. Classic `rest/firewallrule`, `rest/firewallgroup` and `rest/portforward` and v2 `nat` answered with **no records** there, so port forward fields (`name`, `enabled`, `proto`, `dst_port`, `fwd`, `fwd_port`, `pfwd_interface`, `src`) are the legacy ones and unverified, and the classic firewall is deliberately not shown. Do not add a classic reader without real data to check it against.
- Audit (`audit.py`, `Needs(wlans=True, offline=True)`, checked on Network 10.6.106; spiked with GETs only): Wi-Fi networks are legacy `rest/wlanconf` (one record per SSID with `enabled`, `security` of `wpapsk` seen live and `open`/`wep` by the legacy API's convention, `wpa_mode`, `wpa3_support`/`wpa3_transition` (WPA2/WPA3 mixed has both true), `is_guest`, `l2_isolation` (client isolation), `hide_ssid`, `networkconf_id`; it also holds the passphrase in `x_passphrase`, which must never be read or printed). The Integration API `wifi/broadcasts` has `securityConfiguration.type`, `hideName` and `clientIsolationEnabled` but no guest flag, so it is not used. `rest/portconf` had no records, and a port's `native_networkconf_id` against a wired client's `network_id` differs for legitimate reasons on trunk ports (`forward` `all`/`customize` with `tagged_vlan_mgmt` `auto`): 7 of 7 observed mismatches were trunks, so that check was dropped; do not revive it without access-port (`forward` `native`) examples. Findings use the `Finding` of `diagnose` with their own `audit.*` codes in `audit.AUDIT_CODES` (not in `diagnose.CODES`).
- A `CLIENT_IP_CONFLICT` event names the devices in `parameters["CLIENTS"]["clients"]` (a list inside the object, each with `name`, `hostname`, `mac`, `ip`; the `ip` shown can differ from the conflicting address) and the network in `parameters["NETWORK"]`; connect/disconnect events use a single `CLIENT` instead. Merge devices across events by MAC and skip malformed entries.
- Partial `diagnose` runs and notifications: `notify.plan`/`baseline` take the `areas` that ran; a state entry whose code belongs to a skipped area is carried over untouched and never reported recovered (an entry with a code in no area counts as checked). Do not call `plan` for a partial run without `areas`.
- Event checks in `diagnose` read `snap.events` (collected with `Needs(events=EventQuery(...))`, window in `snap.event_window_seconds`); roaming is normal for phones, so it is info only. Use the snapshot's device names in findings so ignore rules match.
- The `client` view lists the client's events (matched by MAC, never by name) from `snap.events`, plus device-state events (`category == "UNIFI_DEVICES"`, no CLIENT parameter) for the devices on its path; internet-latency events also name the gateway but are not shown. `Snapshot.events_available` tells "log unreadable" from "no events".
- Event log: POST `/proxy/network/v2/api/site/{ref}/system-log/all` with `timestampFrom`/`timestampTo` (ms), `pageNumber`, `pageSize` and the server filters `categories`, `severities`, `keys`, `searchText`. Singular names (`category`, `severity`, `types`) are silently ignored, so test a filter by checking the total changes. Records are newest first with `{PLACEHOLDER}` messages filled from `parameters[X].name`; some audit events leave placeholders unresolved. Reading does not change event status.
- Uplinks: a device's legacy `uplink` dict has `uplink_mac` (the parent), `uplink_remote_port` (the PARENT's port), `port_idx` (its own uplink port), `speed` and `max_speed`; a gateway's uplink is its WAN link, not part of the tree. Integration `uplink.deviceId` names the parent when the legacy data does not. An offline device keeps its last known uplink. `DeviceIndex` (client_view.py) and `diagnose.uplink_speeds` are the shared helpers for names, state and negotiated-vs-capability speed.
- Saved snapshots (`history.py`, schema version 1) hold real MACs/IPs: they are written owner-only into the git-ignored `snapshots/`, and tests and docs use only the synthetic fixture. Match by MAC; keep constantly changing values (uptime, last-seen, traffic) out of the record; an unknown location is never a "move". Snapshot file names are UTC (`snapshot-YYYYMMDD-HHMMSSZ[-N].json`; older local-time names without the `Z` are still read) and sort by instant then numeric suffix, never as text; `captured_at` inside the file keeps the local time with its offset.
- DHCP pools (`reservations.dhcp_pool`, checked against Network 10.6.106): `rest/networkconf` has `dhcpd_enabled` (bool, true on `corporate` networks and absent on `wan` and `remote-user-vpn` ones), `dhcpd_start`/`dhcpd_stop` (IP strings, ordered, inside the subnet) and `dhcp_relay_enabled` (false when the gateway serves DHCP); there is no `dhcpd_mode`. A VPN network has a start/stop without `dhcpd_enabled`, so require `dhcpd_enabled is True` and never key off the range alone. `ip_subnet` is the gateway address with a prefix (parse with `strict=False`).
- Offline reservations (`reservations.offline_reservations`): a reservation is offline when its MAC is in neither `snap.clients` nor `snap.devices`; its age is `now - last_seen` from `stat/alluser` (epoch seconds; missing, zero or non-numeric means never seen, a future value is clock skew and counts as 0). `diagnose` and `query reservations --offline` share that function so the listing is exactly what the check reports. The fixture's `last_seen_age_s` is converted to a real timestamp by `FakeSession`, so tests that need a fixed clock pass `now`.
- Randomized MACs (`util.is_randomized_mac`): locally administered unicast means `first_octet & 0x03 == 0x02` (second hex digit 2, 6, A or E); an address with the multicast bit set is never a client, so it is not flagged (the synthetic fixture's `bb:` addresses have both bits set and are therefore not randomized). It is a hint: VMs, containers and bridges use these too. Shown as `Private MAC` in `query clients` and `new-clients` (not in the CSV export), `identity.private_mac` in `client --json`, and two info findings in `diagnose`.
- Networks and Wi-Fi networks (`query networks`, `query wlans`, `query clients --network/--ssid/--ap`; `Needs(networks=True)` reads `rest/networkconf` alone; checked on Network 10.6.106 with GETs only): `rest/networkconf` has `purpose` (`corporate`, `wan`, `remote-user-vpn`); `vlan_enabled` and `vlan` only on the corporate ones and `ip_subnet` not on a WAN network, so a blank VLAN means "not said", not VLAN 1. `rest/wlanconf` has `wlan_bands` (a list of `2g`/`5g`/`6g`), `wpa_mode`, `wpa3_support` and `wpa3_transition` (WPA2/WPA3 mixed has both true, WPA3 only `wpa3_support`) and a `networkconf_id` that always resolved; its `x_passphrase` is in the same record and must never be read (`wlan_rows` reads named fields only, and a test makes the record raise on any other). `stat/sta` records carry `network_id` (resolved for every client, and the client's `network` text was the resolved name), and `wlanconf_id`, which also appears on clients that are not wired but have no `essid`, `ap_mac`, `radio` or `signal` at all (14 of 62 "wireless" clients on the controller checked): a client is on an SSID only when it has an `essid`, then its `wlanconf_id` (or, with no id, the `essid` text) says which network. Client counts are blank, not 0, when `stat/sta` could not be read; an unreadable `rest/networkconf` or `rest/wlanconf` stops `query networks`/`query wlans` with exit code 3 rather than printing an empty table.
- Client group membership is `network_members_group_ids` on legacy client records; group names/ids come from legacy v2 `/proxy/network/v2/api/site/{ref}/network-members-groups` (`client.legacy_v2`).
- Integration API and legacy fields were checked against one live controller (Network 10.6.106). Other versions and hardware may differ, and some fields vary by model (e.g. `mac_table_count` is null on some switches). Verify a new field against real data before relying on it.

## Safety

- Read-only: GET requests only, with **one approved exception**: the event log (`v2/system-log/all`) is POST-only, so `UniFiClient.system_log` sends a read-only query there (approved by the owner for event history, issue #49). It is used by `events` and, by default, by `diagnose` and `client` (`--no-events` skips it); a new feature may reuse it through the snapshot (`Needs(events=...)`) but must not add another POST. It is the only POST: do not add a general POST/PUT/PATCH/DELETE to `UniFiClient`, and do not point `system_log` at any other path. `tests/test_events.py` enforces this. Any other write to the controller needs explicit approval for that specific action.
- Notifications (`notify.py`, issue #85) are the **one outbound channel to anything other than the controller**, approved by the owner for ntfy, a generic webhook and email over SMTP (issue #107, approved 2026-10-02: one plain-text message per run, a provider with an app password, plain SMTP only with the lab opt-in and never with a password) and nothing else (no Slack/Discord adapters or other services without new approval). Rules: opt-in only (`diagnose --notify` and a configured destination; never on by default); the destination URL, token and mail account (host, user, password, addresses) are secrets from the environment, never printed, logged or put in an error (messages carry only the destination kind and a fixed reason; email failures map to fixed phrases in `notify._email_failure`, never the library's text, and the exception order there matters because `SMTPException` and `ssl.SSLError` are `OSError`s); content is limited to the finding identity, severity and text, never the API key, controller address or site id, and `--notify-redact` removes names, addresses and MACs; HTTPS only, TLS verified, redirects not followed; email is STARTTLS or implicit TLS with `ssl.create_default_context()` (never an unverified context, and a password is refused over plain SMTP both in `config.validate_smtp` and in `notify._send_email`); a half-set `NOTIFY_SMTP_*`/`NOTIFY_EMAIL_*` configuration is an error, never a silent no-op; state is owner-only in the git-ignored `snapshots/`. `notify.py` must not import or call `UniFiClient`, and `tests/test_notify.py` enforces that and that it has one `requests.post`, and `tests/test_notify_email.py` that `notify.py` is the only module that imports `smtplib`. It must never write to the controller.
- Contacting the real controller: read-only GET checks (and the approved event-log POST) are fine once the task is approved; summarize or mask what they return and never paste it into the repo. Any other request, anything that changes the controller, and anything that sends data elsewhere needs explicit approval for that specific action. If a feature needs an endpoint nobody has probed yet, say so and get a go-ahead for the GET spike first.
- Never print or commit `.env` or the API key. Redact real MACs, IPs and hostnames in issues, commits, PRs and test fixtures.

## Testing

- Tests are hermetic: an autouse fixture in `tests/conftest.py` runs every test in an empty working directory with `CONTROLLER_URL`, `API_KEY`, `SITE_ID`, `VERIFY_SSL` and `UNIFI_SENTINEL_ENV` unset, because `.env` and `unifi-sentinel.toml` are read from the current directory. Never rely on, or patch around, the developer's real files; a test that needs a file creates it in the working directory or changes directory itself.
- Golden files and docs drift: command output is pinned in `tests/golden/*.txt` (`tests/test_golden.py`, normalised so times and padding do not matter) and the sample blocks in the README and `docs/` must equal it (`tests/test_docs_drift.py`, which also checks that every example in them parses, every command has a Commands row in the README and every long option is mentioned in the README or a docs page; `tests/test_docs_layout.py` keeps the README short and every link and old anchor valid). When you change an output on purpose: `UPDATE_GOLDEN=1 uv run pytest tests/test_golden.py`, then `UPDATE_README_SAMPLES=1 uv run pytest tests/test_docs_drift.py`, and review both diffs. A new command or flag needs its README row and a mention in its docs page, or the suite fails. `tests/test_entry_points.py` and `tests/test_exit_codes.py` cover the launcher, the console script and every documented exit code. Line and branch coverage is 100% and CI enforces it (the `Coverage (100%)` job runs `uv run coverage run -m pytest` and `uv run coverage report`, configured in `pyproject.toml`; a gap fails the pull request): keep it, justify any `pragma: no cover` with a comment, and make a test independent of the Python version that runs it (the TOML reader's errors differ between versions: test with stand-ins). Tests that need `fish` or util-linux `flock` skip where they are missing (a Mac), the cron tests use a stand-in `flock`, so the Coverage job, which installs fish and zsh, is where everything runs; `tests/test_coverage_config.py` pins the job and the settings.
- `FakeSession` deep-copies the fixture for each test, so tests may mutate the data they get; keep it that way.
- Tests use the synthetic fixture `tests/fixtures/controller.json` served by `FakeSession` in `tests/conftest.py`; never hit the live controller from tests, except the opt-in `live` tests below. Add tests for new features and extend the fixture rather than pasting real data (redact MACs, IPs, names).
- The contract (`tests/contract.py`) lists, per endpoint, the fields the code reads: `always` (in every record), `somewhere` (in at least one record of a normal site) and `optional` (only some models, versions or events). Three checks hang on it: `tests/test_contract_fixture.py` fails when the fixture lacks a listed field, when the code reads a field that is not listed (it runs every command through `tests/field_tracking.py` and records each key touched) and when a listed field is never read. So when you read a new field: list it in the contract, then add it to the fixture (and its golden files and the samples in the docs if the output changes). Do not weaken a tier to make a test pass without knowing why the field can be missing.
- Live contract tests: `uv run pytest -m live` (`tests/test_live_contract.py`) reads the real controller once and checks every endpoint against the contract. They are deselected by default (`addopts` in `pyproject.toml`) and in CI, use the real `.env` (the isolation fixture steps aside for tests marked `live`), make GET requests and the one approved event log query (`RecordingSession` raises on anything else) and print endpoint and field names, never values. **They contact the real controller, so ask before running them** (like any other command that does).
- `tools/record_fixture.py` records the controller into `tools/recorded/controller.json` (git-ignored, owner-only) in the shape of the test fixture, keeping only contract fields and passing everything through `tools/sanitize.py`: MACs, addresses, ids, names, SSIDs and the ISP become synthetic values, consistently and deterministically, and `check_no_leaks` refuses to write anything that still holds a real value or an address it did not issue. It also contacts the controller: ask first, and read only its counts and field names; never paste a recording into an issue, a PR or the tests. Change the sanitiser only with tests in `tests/test_sanitize.py` (the leak check must keep rejecting an unmapped address).

## Before opening a PR: review your own diff

Copilot reviews every PR and keeps finding the same kinds of defect (about 15 PRs read: #61 to #119). Look for these in your own diff first, and fix them before pushing; each was a real finding.

1. **Acceptance criteria.** Re-read the issue and list every requirement with the test that proves it in the PR description. A requirement that is not in a test is usually the one that was missed (#73: the controller version in the contract report).
2. **A claim is a test.** Words like "never", "only", "every", "reads less", "no extra requests", "redacted" must be attacked, not assumed: count the requests, poison a value, grep every output path (stdout, stderr, `--verbose`, JSON, errors). Redaction and "never printed" failed at three separate emission points (#98); the recorder's "only contract fields reach disk" failed on an early return (#118); "reads only what it needs" still read every device (#106).
3. **Sibling paths.** When you add behavior to one collector, command, renderer or loader, search for its siblings and apply it or say why not (`collect_event_snapshot` next to `collect_snapshot`, text next to JSON, one command next to the others).
4. **Data edge cases** for every new key, join, dedup, comparison or threshold: missing, empty, `None`, duplicate, a different spelling of the same thing (MAC and IP forms), a display name used as a key (use the id), a non-string, special-use addresses, a limit. An "all traffic" or "every X" condition must check every dimension (ports on both sides, not only the destination). Two records with the same missing field are not duplicates.
5. **Partial failure.** For each optional read that can fail, state what the output then claims and check the rest still works exactly as the warning says (zone names unavailable must not hide every policy). A warning must describe the real impact, not the nearest one.
6. **Mechanical conventions:** a new environment variable goes in `tests/conftest.py` `CONFIG_VARIABLES` (a test enforces it); a new renderer gets a case in `tests/test_output_safety.py`; a new message built from a response or exception goes through `_redact`; no raw exception text on a terminal where a response body can be in it; after moving or splitting code, fix the comments, docstrings and documentation text that still describe the old place ("this module"); tests are exempt from E501 but source is not; a test that needs an invisible or direction-changing character writes it as an escape (`tests/test_no_hidden_characters.py` fails on a raw one).
7. **Tests must be able to fail.** After writing a test, break the thing it guards (remove the field, revert the fix) and watch it fail. No silently skipped parametrizations (a missing console script must fail the collection, not shrink it), no parameter that only appears in the failure message, and a completeness check must force the fallback branches it claims to cover, not only the main ones.
8. **Docs run.** Paste each shell snippet and example you wrote; an example must do what its sentence says (an ignore rule that silences one finding but not the other), catalogue strings must be whole sentences, and every new range or option has to be listed everywhere it applies (IPv6 next to IPv4).
9. **Last read.** Read `git diff main` once as a skeptical reviewer: for every changed line ask what input breaks it and which test would notice.

## Releases

- The owner cuts releases; never create a tag or a GitHub release from here, and do not push a `v*` tag (the release workflow publishes on it). Prepare the pull request, say what remains, and stop.
- Do not bump `unifi_sentinel.__version__` in every PR. Most PRs keep the current version and only add their notes under `CHANGELOG.md` `Unreleased`; the version moves in a dedicated release-prep PR, or in another PR only when the owner explicitly asks.
- To prepare a release PR: review everything under `Unreleased`, choose the next version by the bump rules above (patch/minor/major), change the heading to `## [X.Y.Z] - YYYY-MM-DD`, add a fresh `## [Unreleased]` heading above it for future work, set `unifi_sentinel.__version__` to `X.Y.Z` (the only place; `uv lock` after if the lockfile changes), run the release/check tests, and open the PR. After it merges, the owner runs `git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`.
- `.github/workflows/release.yml` runs only on a pushed `v*` tag: the lockfile check and dependency installation run first, then `tools/release_notes.py` refuses a tag that is not `v` plus `__version__` or an entry without a real date, followed by the tests, `uv build`, and `gh release create --verify-tag` with the entry as notes. It is the only workflow with `contents: write` (on its one job), uses the runner's `gh` CLI rather than a third-party publishing action, and passes the tag through the environment, never into a command line; `tests/test_changelog.py` pins all of that.
- The first release is 0.2.0 (the owner chose it over 0.1.0 and 1.0.0): still 0.x because the endpoints are undocumented, only Network 10.6.106 was tested and the command line may still change.

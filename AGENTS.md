# Homelab Probe

Instructions for every AI coding agent working here (Claude Code, Codex, others); `CLAUDE.md` only imports this file. The rules apply to all agents alike.

A tool for querying, troubleshooting and inventorying a UniFi Network controller. It began as a fork of [ericfitz/unifi-clients-export](https://github.com/ericfitz/unifi-clients-export) but is now a fully standalone project, with no intention of merging anything back into the original; do not open PRs, issues or comments there or design for compatibility with it. Keep the Apache-2.0 license and the credit to the original author.

## Layout

The module-by-module map is in [docs/architecture.md](docs/architecture.md); read it before adding or moving a module. Short version: `hlp.py` is a thin launcher, all logic lives in `homelab_probe/`, `client.py` is the only place that makes HTTP calls, `snapshot.py` is the one read of the controller (a command declares what it reads with a `Needs`), `documents.py` builds the dict that `--json` prints, `diagnose/` and the other analysis modules are pure functions over a `Snapshot`, `commands.py` has one section per subcommand, and `server/` (the `web` extra) is never imported by the core. `web/` is the separate browser UI project. Keep that map current when you add a module or subcommand.

## Commands

- Terminal positional policy: the registry pins `completion.Spec` choices and file-reference metadata, including unavailable commands. Path-typed positionals and diff references are files. Runtime grammar parity requires an explicit policy update, not just a successful CLI parse.
- Terminal API (#272, #273 and #274, tracker #270): `server/terminal_policy.py` owns the explicit command and option allowlist (every alias included), static help/version normalization, limits and the tested matrix in `docs/web.md`. `cli.build_parser(strict=True)` raises fixed `StrictParseError` messages, disables abbreviation on every subparser, rejects repeated scalar options and response-file tokens, and runs pure command validators. It does not execute commands or load configuration. Core code must never import the registry. A new CLI command, option or alias must be explicitly classified or `tests/test_terminal_policy.py` fails. `terminal_api.py` bounds streamed bodies after the app-wide auth guard and submits fixed adapters from `terminal_reports.py` to a per-app bounded pool; only the worker releases execution admission, never HTTP timeout/cancellation. `terminal_completion.py` uses only static role-filtered parser/registry metadata, with tokenized input and Unicode codepoint cursors; no handlers, configuration, files or controller access. Completion shares execution admission but releases synchronously; no suggestion cache. `report_validation.py` shares report-route checks. Redact data before both text and JSON rendering, and bound warnings/candidates too. Wire schemas in `docs/terminal/` are generated by `python -m tools.generate_terminal_contracts` and checked by the terminal tests; regenerate web types and OpenAPI with contract changes. The #269 handoff and schema-checked mock fixture are linked from `docs/web.md`.
- Run: `uv run hlp.py <export|query|client|new-clients|diagnose|events|wan|firewall|audit|wifi|topology|snapshot|diff|doctor|completion|web-user|info>`
- `make` lists shortcuts (`make check`, `make ci`, `make clean`); `make clean` is safe; never run `git clean` here (git-ignored real data) or `make tag`.
- Tests: `uv run pytest`. Lint: `uv run ruff check .` (add `--fix` for import order and unused imports). Types: `uv run mypy` (clean, and blocking in CI: fix a finding with a real narrowing or type, not a `# type: ignore`, which `warn_unused_ignores` would also police). The shapes worth naming are `TypedDict`s: the saved snapshot (`history.SnapshotRecord` with `DeviceRecord`, `ClientRecord`, `ReservationRecord`; `Diff`/`DiffPart`/`Change`), the topology (`topology.Topology`, `Node`, `Summary`) and the Wi-Fi rows (`wifi.Radio`, `Neighbor`). Controller payloads (`Snapshot.devices`, `legacy_clients`, ...) stay `Dict[str, Any]` on purpose: they are undocumented and vary by model, so typing them would claim knowledge we do not have. A record that is read back from disk (`load_snapshot`) is validated first and then cast, because `isinstance` cannot check a `TypedDict`. When you add a key to one of these, add it to the TypedDict: `tests/test_typed_records.py` compares each TypedDict with the keys of a real capture, tree and radio/neighbor list (Python 3.10 has no `NotRequired`, so a key that exists only sometimes goes in a `total=False` subclass, as `Node` does); use `util.record_for` to look up a record by an id that may be missing. Lockfile: `uv lock --check`. CI (`.github/workflows/ci.yml`) runs all of these on every push to `main` and every PR, tests on Python 3.10 to 3.13; run `uv run pytest` and `uv run ruff check .` before pushing. The minimum Python is 3.10.

## Conventions

- Names (the project was renamed before its first release; see #160): the project and distribution are `homelab-probe`, the Python package `homelab_probe`, the command `hlp` (launcher `hlp.py`), the settings file `hlp.toml`, the variable naming the `.env` file `HLP_ENV`. **UniFi is the primary and, for now, only supported platform** (more may come, see "Platforms" in #160): its connection settings are prefixed `UNIFI_` (`UNIFI_URL`, `UNIFI_API_KEY`, `UNIFI_SITE_ID`, `UNIFI_VERIFY_SSL`, `UNIFI_TIMEOUT`, `UNIFI_PARALLEL_REQUESTS`) and a later platform gets its own prefix; `ALLOW_INSECURE_HTTP`, `NOTIFY_*`, `LOG_*` and `HLP_ENV` are shared. Finding codes are never renamed, so UniFi's stay unprefixed and another platform's codes must carry its name (`proxmox.vm.stopped`); nothing UniFi-specific goes into a name that every platform would share. Do not write the old names (`tests/test_project_name.py` fails on them) and do not widen the "tested on Network 10.6.106" claim.
- Documents (`documents.py`, issue #178): a new command is a builder plus renderers, never a handler that prints data: `build_x(snapshot, ...)` (pure, in its module), `x_document(...)` in `documents.py` (reads with a `Needs` constant, returns a `Document` whose `data` is exactly what `--json` prints, `version` first, JSON-serializable, raw values), and a handler that only parses, calls the document function, renders `document.data` and prints. The text renderer takes the dict, so `--json`, the text and a later API cannot drift; warnings are in `document.warnings` (`echo=True` on the command line keeps `Warning:` on stderr in the same order, `echo=False` for an API). `documents.py` prints nothing and imports only the standard library and this package (never `server/`, never a third-party package; `tests/test_documents.py` checks both).
- Reading the controller: a new read is a new field of `snapshot.Needs` plus the code that honors it, and every command passes the smallest `Needs` it uses (`tests/test_needs.py` pins which endpoints each command reads, so a command that starts reading more fails the suite until its declaration and the test agree). Required data (`users_required`) fails the command; everything else degrades with a warning.
- Shared helpers live in `util.py` and are imported; do not define a private copy of one in a module (the same `_num` once existed in five places), and do not import another module's underscore-prefixed names. `tests/test_util_helpers.py` tests them directly.
- Stdlib `csv`, not pandas. Match the surrounding style; type-hint public functions.
- Configuration (`config.py`): the `.env` file comes from `--env-file`, then `HLP_ENV`, then `./.env` in the current directory only (never the package directory or parent directories). Validate every setting (`UNIFI_VERIFY_SSL` words, `UNIFI_SITE_ID` characters (and `--site`, which beats `UNIFI_SITE_ID` and goes through the same `validate_site`, naming the option in its messages), `UNIFI_URL` scheme and host, `http://` only with `ALLOW_INSECURE_HTTP`) and percent-encode site references in URL paths. The API key is never printed: `Config.api_key` is `repr=False`, `UniFiClient._redact` strips it from response bodies and exception text, and a loose-permission `.env` gives a warning (`Config.warnings`, printed by `cli.main`), never an error. Any new message built from a response or an exception goes through `_redact`.
- Output safety (`util.py`): names (clients, devices, SSIDs, event text) are untrusted. Text renderers call `clean_data` on their report (or `printable` on single values; `format_table` cleans every cell), every CSV cell goes through `csv_safe` (for output that reaches `say`, clean the text with `printable` first, as `query.csv_cell` does: `say` strips control characters afterwards and would otherwise expose a formula hidden behind an escape character), and `commands.say` is the print backstop; never use a bare `print` for data in `commands.py` or `cli.py`. JSON output stays raw. A new renderer needs a case in `tests/test_output_safety.py`. `export --format json` follows the same split: its values are raw (`unifi_inventory.json`, git-ignored because it holds real MACs and IPs) while its CSV files go through `csv_safe`, and the two must stay the same data (`tests/test_export_json.py` compares them).
- Ignore rules (`settings.IgnoreRule`) match a finding's `code` exactly (case-sensitive, no wildcards) as well as `subject` (wildcards) and `message` (substring); all given fields must match and a rule needs at least one. A `code` must be in `settings.known_codes()` (`diagnose.CODES` plus `audit.AUDIT_CODES`; imported lazily because `diagnose` imports `settings`), otherwise loading fails with the valid codes listed. A new command that produces findings and applies ignore rules must add its codes to `known_codes`. A `Finding` built without a code never matches a code rule. An optional `until` date (a TOML date or a `YYYY-MM-DD` string, nothing else) is the last day a rule applies: `apply_ignores(findings, rules, today=None)` skips expired rules (tests pass `today`, or use dates far in the past or future), and `diagnose` and `audit` print one stderr warning per expired rule (`_warn_expired_rules`; never an exit code). The allowed keys are `code`, `subject`, `message`, `reason` and `until`.
- Subsystem rules (JSON documents and schemas, `doctor` check ids, HTTP, `--verbose`, logging, parallel reads) are in [docs/agent-reference.md](docs/agent-reference.md#conventions). Follow them.
- Finding codes: every `Finding` built by a check in the `diagnose` package passes `code=` with a key of `diagnose.CODES` (`area.problem`, lower case). A code is an interface for `diagnose --json` and scripts: never rename or reuse one, add new ones to `CODES` and to the code table in `docs/diagnose.md`. `tests/test_diagnose_json.py` scans the source (a missing, unknown or unused code fails) and pins the list. The JSON document has a `version`; bump it only when a field is removed or renamed.
- Degradation policy: required data (devices, connected clients) fails the command; every legacy read is optional and warns, except `stat/alluser` for `new-clients` and `snapshot`/`diff`, which pass `users_required=True` because their output would be wrong without it.
- Raise `UniFiAPIError`/`ConfigError`; only `cli.main` turns them into messages and exit codes (it also turns an `OSError` from a file the command could not read or write into `ERROR: <reason> (<path>)` and exit 3, never a traceback; do not catch it yourself just to print).
- MACs are compared only through `util.normalize_mac` (upper case with colons, whatever separators the source used); never `(x or "").upper()` on a MAC, `tests/test_mac_formats.py` scans for it and re-spells every source's MACs across all commands. Likewise IPs through `normalize_ip`, and join records by id, never by a display name.
- Exit codes: 0 success, 1 and 2 are reserved for `diagnose` and `audit` findings (warning, critical; `audit` has no critical), 3 is a config/connection error, 4 is `client` finding no single match, 64 is a usage error. Do not reuse 1 or 2 for errors.
- The version is written once, as `homelab_probe.__version__`; `pyproject.toml` reads it (`dynamic = ["version"]` with `[tool.setuptools.dynamic]`), so bump it only there (`tests/test_accuracy.py` checks the wheel, `--version` and that nothing else repeats it). A PR changes `__version__` only when it is explicitly preparing a release or when the owner asks for a version bump; ordinary feature, fix, docs and dependency PRs add to `CHANGELOG.md` under `Unreleased` and leave the version alone. When asked to bump for a release, choose the next version from the unreleased changes: patch for bug fixes, docs that affect installed/released artifacts, dependency/security updates and small compatibility fixes; minor for new commands, flags, settings, output columns, checks, notification destinations, schemas or other user-visible capability; major only for a deliberate breaking change after owner approval (the project should normally stay `0.x` while the CLI and undocumented-controller behavior can still change). The README says only Network 10.6.106 was tested: do not widen that claim without testing.
- Dependencies are declared only in `pyproject.toml`; run `uv lock` after changing them and commit `uv.lock`.

## UniFi API notes

Field-level findings about the controller's API (endpoints, which fields exist, what was checked on Network 10.6.106) are in [docs/unifi-api-notes.md](docs/unifi-api-notes.md); read the relevant note before touching code that reads that data, and add what you learn there. ## Safety

- Read-only: GET requests only, with **one approved exception**: the event log (`v2/system-log/all`) is POST-only, so `UniFiClient.system_log` sends a read-only query there (approved by the owner for event history, issue #49). It is used by `events` and, by default, by `diagnose` and `client` (`--no-events` skips it); a new feature may reuse it through the snapshot (`Needs(events=...)`) but must not add another POST. It is the only POST: do not add a general POST/PUT/PATCH/DELETE to `UniFiClient`, and do not point `system_log` at any other path. `tests/test_events.py` enforces this. Any other write to the controller needs explicit approval for that specific action.
- Notifications (`notify.py`, issue #85) are the **one outbound channel to anything other than the controller**, approved by the owner for ntfy, a generic webhook and email over SMTP (issue #107, approved 2026-10-02: one plain-text message per run, a provider with an app password, plain SMTP only with the lab opt-in and never with a password) and nothing else (no Slack/Discord adapters or other services without new approval). Rules: opt-in only (`diagnose --notify` and a configured destination; never on by default); the destination URL, token and mail account (host, user, password, addresses) are secrets from the environment, never printed, logged or put in an error (messages carry only the destination kind and a fixed reason; email failures map to fixed phrases in `notify._email_failure`, never the library's text, and the exception order there matters because `SMTPException` and `ssl.SSLError` are `OSError`s); content is limited to the finding identity, severity and text, never the API key, controller address or site id, and `--notify-redact` removes names, addresses and MACs; HTTPS only, TLS verified, redirects not followed; email is STARTTLS or implicit TLS with `ssl.create_default_context()` (never an unverified context, and a password is refused over plain SMTP both in `config.validate_smtp` and in `notify._send_email`); a half-set `NOTIFY_SMTP_*`/`NOTIFY_EMAIL_*` configuration is an error, never a silent no-op; state is owner-only in the git-ignored `snapshots/`. `notify.py` must not import or call `UniFiClient`, and `tests/test_notify.py` enforces that and that it has one `requests.post`, and `tests/test_notify_email.py` that `notify.py` is the only module that imports `smtplib`. It must never write to the controller.
- Contacting the real controller: read-only GET checks (and the approved event-log POST) are fine once the task is approved; summarize or mask what they return and never paste it into the repo. Any other request, anything that changes the controller, and anything that sends data elsewhere needs explicit approval for that specific action. If a feature needs an endpoint nobody has probed yet, say so and get a go-ahead for the GET spike first.
- Never print or commit `.env` or the API key. Redact real MACs, IPs and hostnames in issues, commits, PRs and test fixtures.

## Testing

- Tests are hermetic: an autouse fixture in `tests/conftest.py` runs every test in an empty working directory with `UNIFI_URL`, `UNIFI_API_KEY`, `UNIFI_SITE_ID`, `UNIFI_VERIFY_SSL` and `HLP_ENV` unset, because `.env` and `hlp.toml` are read from the current directory. Never rely on, or patch around, the developer's real files; a test that needs a file creates it in the working directory or changes directory itself.
- Golden files and docs drift: command output is pinned in `tests/golden/*.txt` (`tests/test_golden.py`, normalised so times and padding do not matter) and the sample blocks in the README and `docs/` must equal it (`tests/test_docs_drift.py`, which also checks that every example in them parses, every command has a Commands row in the README and every long option is mentioned in the README or a docs page; `tests/test_docs_layout.py` keeps the README short and every link and old anchor valid). When you change an output on purpose: `UPDATE_GOLDEN=1 uv run pytest tests/test_golden.py`, then `UPDATE_README_SAMPLES=1 uv run pytest tests/test_docs_drift.py`, and review both diffs. A new command or flag needs its README row and a mention in its docs page, or the suite fails. `tests/test_entry_points.py` and `tests/test_exit_codes.py` cover the launcher, the console script and every documented exit code. Line and branch coverage is 100% and CI enforces it (the `Coverage (100%)` job runs `uv run coverage run -m pytest` and `uv run coverage report`, configured in `pyproject.toml`; a gap fails the pull request): keep it, justify any `pragma: no cover` with a comment, and make a test independent of the Python version that runs it (the TOML reader's errors differ between versions: test with stand-ins). Tests that need `fish` or util-linux `flock` skip where they are missing (a Mac), the cron tests use a stand-in `flock`, so the Coverage job, which installs fish and zsh, is where everything runs; `tests/test_coverage_config.py` pins the job and the settings.
- Demo mode, the live contract tests and the fixture recorder have their rules in [docs/agent-reference.md](docs/agent-reference.md#testing). Live tests and the recorder contact the real controller: ask first.
- `FakeSession` (`DemoSession`) deep-copies the fixture for each test, so tests may mutate the data they get; keep it that way.
- Tests use the synthetic fixture `homelab_probe/demo/controller.json` served by `FakeSession` in `tests/conftest.py`; never hit the live controller from tests, except the opt-in `live` tests below. Add tests for new features and extend the fixture rather than pasting real data (redact MACs, IPs, names).
- The contract (`tests/contract.py`) lists, per endpoint, the fields the code reads: `always` (in every record), `somewhere` (in at least one record of a normal site) and `optional` (only some models, versions or events). Three checks hang on it: `tests/test_contract_fixture.py` fails when the fixture lacks a listed field, when the code reads a field that is not listed (it runs every command through `tests/field_tracking.py` and records each key touched) and when a listed field is never read. So when you read a new field: list it in the contract, then add it to the fixture (and its golden files and the samples in the docs if the output changes). Do not weaken a tier to make a test pass without knowing why the field can be missing.

## Before opening a PR: review your own diff

Copilot reviews every PR and keeps finding the same kinds of defect (about 15 PRs read: #61 to #119). Look for these in your own diff first, and fix them before pushing; each was a real finding.

1. **Acceptance criteria.** Re-read the issue and list every requirement with the test that proves it in the PR description. A requirement that is not in a test is usually the one that was missed (#73: the controller version in the contract report).
2. **A claim is a test.** Words like "never", "only", "every", "reads less", "no extra requests", "redacted" must be attacked, not assumed: count the requests, poison a value, grep every output path (stdout, stderr, `--verbose`, JSON, errors). Redaction and "never printed" failed at three separate emission points (#98); the recorder's "only contract fields reach disk" failed on an early return (#118); "reads only what it needs" still read every device (#106).
3. **Sibling paths.** When you add behavior to one collector, command, renderer or loader, search for its siblings and apply it or say why not (`collect_event_snapshot` next to `collect_snapshot`, text next to JSON, one command next to the others).
4. **Data edge cases** for every new key, join, dedup, comparison or threshold: missing, empty, `None`, duplicate, a different spelling of the same thing (MAC and IP forms), a display name used as a key (use the id), a non-string, special-use addresses, a limit. An "all traffic" or "every X" condition must check every dimension (ports on both sides, not only the destination). Two records with the same missing field are not duplicates.
5. **Partial failure.** For each optional read that can fail, state what the output then claims and check the rest still works exactly as the warning says (zone names unavailable must not hide every policy). A warning must describe the real impact, not the nearest one.
6. **Mechanical conventions:** a new environment variable goes in `tests/conftest.py` `CONFIG_VARIABLES` (a test enforces it); a new renderer gets a case in `tests/test_output_safety.py`; a new message built from a response or exception goes through `_redact`; no raw exception text on a terminal where a response body can be in it; after moving or splitting code, fix the comments, docstrings and documentation text that still describe the old place ("this module"); tests are exempt from E501 but source is not; a test that needs an invisible or direction-changing character writes it as an escape (`tests/test_no_hidden_characters.py` fails on a raw one).
7. **Tests must be able to fail.** After writing a test, break the thing it guards (remove the field, revert the fix) and watch it fail. No silently skipped parametrizations (a missing console script must fail the collection, not shrink it), no parameter that only appears in the failure message, and a completeness check must force the fallback branches it claims to cover, not only the main ones.
8. **Docs run.** Paste each shell snippet and example you wrote; an example must do what its sentence says (an ignore rule that silences one finding but not the other), catalogue strings must be whole sentences, and every new range or option has to be listed everywhere it applies (IPv6 next to IPv4).
9. **Last read.** Read `git diff main` once as a skeptical reviewer: for every changed line ask what input breaks it and which test would notice.

## Releases

- The owner cuts releases; never create a tag or a GitHub release from here, and do not push a `v*` tag (the release workflow publishes on it). Prepare the pull request, say what remains, and stop.
- Do not bump `homelab_probe.__version__` in every PR. Most PRs keep the current version and only add their notes under `CHANGELOG.md` `Unreleased`; the version moves in a dedicated release-prep PR, or in another PR only when the owner explicitly asks.
- **Tell the owner when a release is due; do not wait to be asked, and never do it yourself.** At the end of a task (after a PR merges, or when asked what is next), look once at whether a release makes sense and, if it does, say so in a couple of lines: the version you would pick and why (by the bump rules above), what is in `Unreleased`, and that the next step is a release-prep PR followed by the owner's tag. Then continue with what was asked. Check with `git tag --list 'v*'` and `git log <latest tag>..main --oneline` (before the first tag, everything under `Unreleased` counts), the `CHANGELOG.md` `Unreleased` entry, `gh run list --branch main --limit 3` and `gh pr list`. Raise it when **all** of these hold: `main` has user-visible changes that no tag contains; the latest CI run on `main` passed; no open PR is half of a feature that belongs in the same release (a command whose second PR is still open, or a change waiting on review that the changelog already mentions); and either (a) it is a **security fix, a bug fix people would notice, or a change to an exit code, finding code or JSON `version`**, which is worth releasing soon on its own (a patch, or a minor if the change is breaking), or (b) a **coherent batch is finished**: the issues being worked on together are merged and nothing is left in progress, which is usually a new command, flag, check or setting (a minor). Do not raise it for docs-only, test-only or CI-only changes, for a change that is not merged yet, after every PR, or again in the same session once the owner has said "not yet"; ask again only when something new qualifies. If the owner says yes, prepare the release-prep PR as described below and stop at the PR.
- Follow [MAINTAINING.md](MAINTAINING.md#prepare-a-release) for the release-prep PR and [Tag and Publish](MAINTAINING.md#tag-and-publish) for the owner's tagging steps and automated release behavior. Keep those procedures current in that file rather than duplicating them here. `tests/test_changelog.py` pins the release workflow's validation and publishing rules.
- The first release is 0.2.0 (the owner chose it over 0.1.0 and 1.0.0): still 0.x because the endpoints are undocumented, only Network 10.6.106 was tested and the command line may still change.

## Git and GitHub

- Commit only when asked. When asked to check in code, always create a feature branch and open a PR; never commit to `main`.
- Open the PR and stop; do not merge it. PRs normally wait for a GitHub Copilot code review, and the user merges after addressing it. Merge only when the user explicitly asks for that PR.
- When addressing a Copilot code-review comment, always reply in the original review thread with the changes made, the relevant commit, and validation results (or explain why no change was made). A PR description update or separate summary comment does not replace the thread reply: keep the conversation traceable so it can be followed and marked resolved.
- GitHub still records this repo as a fork, so always pass `--repo jeffholst/homelab-probe` to `gh pr create`; the default target is the original repo, which must never receive a PR.
- Keep local branches clean. Never work on `main`; it only moves via `git pull`. Start each branch from an up-to-date `main` unless the work depends on an open PR. Keep the PR branch (and stay on it) while the PR is open, since review fixes are pushed to it.
- After a PR is merged, clean up: `git checkout main && git pull`, then `git branch -d <branch>` (`-d` refuses if unmerged, so it doubles as a check; use `-D` only after confirming the PR is merged, e.g. after a squash merge). `fetch.prune` is enabled globally and the repo deletes head branches on merge, so `origin/*` refs clean themselves up. Before finishing a task, check `git branch -vv` and delete any local branch whose PR is merged; leave branches with open PRs alone.
- Dependabot (`.github/dependabot.yml`: the GitHub Actions, `uv.lock` and the `Dockerfile` base images, weekly, one grouped PR per ecosystem) opens PRs like any other: nothing merges until the owner asks, CI must be green (tests on Python 3.10 to 3.13, ruff, mypy, `uv lock --check`), and a bump that changes `uv.lock` is reviewed for its changelog and for new transitive dependencies. Keep actions pinned to exact tags (`astral-sh/setup-uv` publishes no floating `v10`; `tests/test_dependabot_config.py` enforces it). Dependabot alerts and security updates are repository settings only the owner can switch on (Settings, Advanced Security); do not try to do it from here.
- Track work in GitHub issues (`jeffholst/homelab-probe`) and reference them in commits and PRs. Give a new issue an `area:` label and any status labels it needs (`blocked`, `needs-approval`, `deferred`, `tracker`, `launch`, `terminal`, `security`); the meaning of each is in `MAINTAINING.md` ("Issue Labels"), and the issue forms add only `bug` or `enhancement`. Pushing and issue creation need the `jeffholst` gh account active (`gh auth switch -u jeffholst`).

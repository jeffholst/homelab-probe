# Changelog

All notable changes to Homelab Probe are listed here, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the version numbers follow
[Semantic Versioning](https://semver.org/) as far as a 0.x project can: while the major version is 0, a minor
version may change behavior, and anything that does is listed under **Changed**.

This project is a fork of [ericfitz/unifi-clients-export](https://github.com/ericfitz/unifi-clients-export). The
`export` command and its CSV layout come from that project.

## What scripts can rely on

These are the parts of the interface that scripts, cron jobs and dashboards depend on. A change to any of them is
always listed here.

- **Exit codes:** `0` success (for `diagnose` and `audit`: no finding at or above `--fail-on`); `1` a warning (or
  `--fail-on info` finding); `2` a critical finding (`diagnose` only); `3` a configuration, connection, controller, or
  file read/write error (also `diagnose --notify` when the findings gave `0` but no message could be delivered); `4`
  `client` found no single match; `64` a command-line usage error. `1` and `2` are never used for errors.
- **Finding codes** (`device.offline`, `port.slow_link`, `audit.wifi_open`, ...) are never renamed or reused; new
  ones are added. They are what `--json` output and ignore rules (`[[ignore]] code = ...`) use.
- **JSON documents** carry a `version` as their first key (every `--json` output that is an object, and the webhook
  payload, are version `1`; the plain lists of `query`, `new-clients` and `events` are bare arrays and have none),
  and each has a JSON Schema in `docs/schemas/`. It changes when a field is removed, renamed or its meaning changes; new fields may appear without a new version.
- **Saved snapshots** (`snapshot`, `diff`) have `schema_version` `1`; a file of another version is refused with a
  clear message, never misread.
- The package never changes anything on the controller. Every request is a GET, with one read-only exception: the
  event log can only be queried with a POST (`events`, and `diagnose` and `client` unless `--no-events`).

## [Unreleased]

### Changed

### Fixed

### Added

- **Style-only CSP nonces for the terminal preview (#310):** preview builds authorize xterm's generated styles with fresh per-document nonces without allowing arbitrary inline styles or scripts. Nonce-bearing HTML is never cached; API and asset policies stay unchanged. Normal terminal builds remain disabled pending final acceptance.

- **Gated browser terminal API integration (#277):** an explicit `VITE_TERMINAL_API_PREVIEW=1` build connects the panel to authenticated capabilities, explicit-Tab completion and read-only execution through the shared cookie/CSRF client, without execution retries or query-cache storage. Replies are matched to request IDs, malformed replies are refused, server warnings and truncation are shown (including an explicit notice for incomplete completion suggestions), and failures distinguish did-not-run, failed and unknown outcomes. Session disposal aborts waiting and drops late replies; user changes clear the terminal, and an aborted request's late 401 cannot end a newer session. Normal builds remain disabled pending the CSP decision. See [docs/web.md](docs/web.md#browser-terminal-api-integration).

- **Browser terminal engine foundation (#275):** a pure TypeScript command-line model with grapheme-aware editing, bounded in-memory history, explicit multiline-paste confirmation, literal tokenization, metadata-derived suggestions, stale-completion protection, single-execution admission and terminal cell-width wrapping. Streaming input decoding keeps paste boundaries across chunks and drains oversized pastes without submitting. The xterm panel and real API integration remain separate work; no browser terminal is enabled by this change. See [docs/web.md](docs/web.md#terminal-command-line-engine).

- **The terminal panel in the web app (#276, part of #269):** a docked panel (open, collapsed, expanded, closed; resizable by pointer or keyboard; light and dark; phone and desktop layouts with an always-visible shortcut toolbar) that draws the command line with xterm.js, lazily loaded the first time it is opened. The engine owns the line; every character of report text is cleaned before it is written, so a report cannot move the cursor, change the title, overwrite the prompt or forge a status line. Ctrl+C while a command runs says that waiting stopped, never that the command was cancelled. The `VITE_TERMINAL_MOCK=1` build uses a mock backend and the real command-line engine; the stand-in engine remains in tests. **A normal build contains no terminal** until the real API is connected (#277); the browser tests use the mock build. Adds `@xterm/xterm` and `@xterm/addon-fit` to `web/` only. Open decision recorded in `docs/development.md`: xterm.js needs inline `<style>` elements, which the server's content-security policy blocks.

- **New devices without tagging (#300):** `new-clients` now lists the clients the controller first saw within `--since` (default `7d`; `90m`, `24h`, `2w`), using the `first_seen` time the controller records, so nobody has to put a device in a client group for it to show. **Changed:** with no option it no longer lists the clients in no group; that list is `new-clients --ungrouped` (with `--ungrouped` alone there is still no age limit, and with both options a client must be new and in no group). A client without a usable first-seen time is unknown, never new, and the footer counts them. `--since` and `--ungrouped` are also parameters (`since`, `ungrouped`) of `GET .../new-clients` and options of the terminal. The JSON stays a bare array with the same columns. New `diagnose` finding `client.new_device` (information, subject the client's MAC address) for each client first seen within the new threshold `new_client_window_hours` (default 24, `0` turns it off); the `clients` area now also reads the client history (`stat/alluser`, a warning if it cannot be read); information findings are sent by `--notify` only with `--notify-min info`.

- **Secure terminal API (#272, #273 and #274, tracker #270):** an opt-in strict CLI parser and explicit web capability registry classify every command and option, pin positional choices and file-reference metadata, and reject unreviewed browser capabilities and grammar drift. Authenticated capabilities, static completion and execute endpoints expose reviewed read-only reports in-process, with strict bounded requests, safe text/JSON output, audit events, shared rate/concurrency limits and worker-owned execution slots after timeout or disconnect. Completion suggests only role-filtered grammar metadata, never files or dynamic controller values. Generated schemas/types, option repeatability and comma-list metadata, mock responses and the integration handoff support the browser terminal (#269). Normal CLI behavior is unchanged. See [docs/web.md](docs/web.md#the-terminal-api).

- **The dashboard in the web app (#187):** the first page after the login now shows how the network is: a status headline (healthy only for a complete, fresh read of a controller that answered; a partial, old or unreachable read says so instead), the open findings to look at first, devices, clients, the internet connection, Wi-Fi and the notable events of the last 24 hours, from the existing `GET /api/v1/unifi/sites/{site}/dashboard`. A section that was not read says so rather than showing zero, an unknown number reads "Unknown", and a site picker appears when the controller has several sites. This replaces the placeholder home page. See [docs/web.md](docs/web.md#the-dashboard-page).

- **A branded web interface and the guided setup in the browser (#267, part of #187):** the web app has a new look built from the logo: dark by default ("night ops" navy with the electric blue and the ant's orange), a polished light theme and a system option; a sticky header with the ant mascot, the navigation and an account menu (a menu sheet on a phone or tablet), a footer with the version and the project's links, and a refreshed login with the full logo. A server in its setup mode now sends the app to `/setup`: enter the setup token (kept in the page's memory only), then **set up a new installation** (the controller and API key, pinning its certificate by fingerprint or the other choices, the connection test and a site picker, optional notifications with a dry run, an optional first health check, and the first administrator; when the settings cannot be saved on the server, the finished `.env` and compose snippet with placeholders for the secrets) or **restore from a backup** (open a `.hlpbackup` file with its passphrase, read what the restore would do, confirm, with a passphrase for the recovery backup when there is a present state). The admin mode offers the first administrator only. The API key, notification values, passphrases and token are never stored in the browser, kept in the page's query cache or shown again; a read-only server says on the first screen that it cannot save a setup or restore a backup, and a connection test that passes with warnings says so. See [docs/web.md](docs/web.md#the-setup-screens).

- **Compact CLI identity (#236):** enhanced `diagnose`, `audit`, `query` and `new-clients` output starts with `Homelab Probe | Command | resolved-site`, once per invocation, with literal, safely wrapped site names and no extra requests. No banner in plain, machine-readable, redirected, narrow, dumb, CI, watch or `--no-emoji` output. See [docs/configuration.md](docs/configuration.md#compact-command-headings-and-help).
- **Findings and tables on a terminal (#235):** with the `pretty` extra on a terminal, `diagnose` and `audit` group their findings by severity (red critical, yellow warning, cyan headings; every finding keeps its written label, subject and code; long messages wrap behind a bar so a wrapped line cannot look like a finding) and end with a summary of the counts, the ignored findings and the elapsed time, which never calls a partial read healthy; `query` and `new-clients` print aligned tables with colored states, and stacked rows on a terminal too narrow for the table, cutting nothing. Exit codes, `--json`, `--csv`, exports and plain output (`--plain`, no extra, not a terminal) are unchanged. See [docs/configuration.md](docs/configuration.md#findings-and-tables-on-a-terminal).
- **Progress while a command reads the controller (#234):** a command that takes more than about 0.2 seconds shows one transient line on stderr, redrawn in place (a spinner, what it is really waiting for, such as `Reading devices`, and the elapsed time), for `audit`, `client`, `diagnose`, `diff`, `events`, `firewall`, `info`, `new-clients`, `query`, `snapshot`, `topology`, `wan` and `wifi`. It needs the `pretty` extra and a terminal on stderr, is off with `--no-progress`, `--plain`, `--verbose`, `CI`, `TERM=dumb`, a terminal under 40 columns, machine-readable output and `diagnose --watch`/`--notify`, never touches stdout, writes nothing for a quick command, never shows a percentage or an estimate, keeps a warning on a clean line, ends at the command's first output and restores the cursor on success, error and Ctrl+C. See [docs/configuration.md](docs/configuration.md#what-the-progress-line-shows).
- **Self-service password change (#241):** `POST /api/v1/auth/password` lets any logged-in user (a viewer too) change their own password with `current_password` and `new_password`. The current password is checked through the same throttle as a login (`429 too_many_attempts` while a wait lasts; a wrong one is `422 invalid_current_password`), the new one follows the existing rule (`422 invalid_password` with the fixed sentence of the rule, checked before the current password so it does not count as a guess), every other session of the user ends and the caller gets a new session (new cookie and `csrf_token` in the answer, the same login start). Audited as `user.password_changed` (and `auth.password_failed` / `auth.throttled` for a wrong current password), never with a password; refused by `serve --read-only`. `GET /api/v1/auth/me` and the login answer gain `can_change_password`. See [docs/web.md](docs/web.md#changing-your-own-password-post-apiv1authpassword).
- **`topology --format mermaid|dot` (#164):** draws the uplink tree as a Mermaid flowchart or a Graphviz DOT digraph, to paste into a README, a wiki page, a ticket or a dashboard (`--format text` is the tree as before and the default). Each device is a node with its model, client count, `OFFLINE` and its worst finding (`WARNING x8`); each uplink is an edge from the parent labelled with the parent's port and the negotiated speed (`port 2, 100 Mbps, supports 1000`, dashed when the device is offline); critical, warning and offline devices are colored and dashed; devices that cannot be reached from a gateway are in a subgraph of their own; `--clients` adds the wired clients as nodes. Nothing from the network is ever syntax: node ids are generated (`n0`, `c0`), Mermaid labels are quoted with every ASCII punctuation character written as an entity, DOT labels escape `\\`, `"` and `&`, and the tests check every line against a strict grammar with hostile names. The graph formats cannot be combined with `--json` (usage error, exit code 64). The `--json` document and the text view are unchanged. See [docs/network.md](docs/network.md#graph-formats).
- **The server serves the built web app (#242):** a bundle in `homelab_probe/web/` (an `index.html` and hashed files under `assets/`, the output of the web app's build; git-ignored and shipped in the wheel as package data, which needs setuptools 62.3 to build) is served at `/`. A deep link such as `/findings/abc` answers `index.html` (never cached), `/assets/*` are cached for a year (`immutable`), and `/api/...`, `/healthz` and `/readyz` are never shadowed (an unknown API path stays the JSON `404`). Only `GET` and `HEAD` are matched. Only files of the bundle can be read: `..`, encoded traversal, backslashes, hidden files and symbolic links are refused (each file is opened without following links and served from the opened descriptor, so a swap between check and open cannot leak a file) and a directory is never listed. These routes are public (the login page must load) and hold nothing but the bundle. The web app's responses carry a Content-Security-Policy for a page (own scripts, styles, images and fonts only, no inline code, no eval, no framing); the API's stays as strict as before. A checkout with no bundle is API only, and `/` shows a notice that says how to get the interface. `HEAD /` now answers 200. See [docs/web.md](docs/web.md#the-web-app-files).
- **Findings that share a cause (#186, #230):** each finding of `GET /api/v1/unifi/sites/{site}/findings` (and the answer of `PUT .../triage`) has a new `group`: `null`, or, where the uplink topology supports it, the finding that probably explains it. The first case is a device that is offline behind an offline uplink: `group` has the `kind` `offline_behind_offline_uplink`, the `cause` (the id of the root-most offline device's own `device.offline` finding), the `evidence` (the uplink chain with names, MACs, ports and finding ids) and the `limitations` (an offline device keeps its last known uplink, so this is a probable cause, never a confirmed one). A device with no known uplink, an online parent, a parent without a finding or a loop in the uplinks is not grouped. Nothing is hidden: every finding stays in the list at the same rank and the counts do not change. No new request to the controller.
- **Global search over the API (#245):** `GET /api/v1/unifi/sites/{site}/search?q=` finds clients (including those not connected now), devices, Wi-Fi networks, networks, findings and the subjects of notes (by their last-known name, so a device that is gone can still be found) in one request, for both roles. `q` is 2 to 64 characters and never a pattern; a MAC or an IP matches in any spelling; `limit` (default 10, at most 50) bounds each kind and `truncated` says when something was cut; the order is deterministic (best match first). Names come back exactly as the controller wrote them, a source that could not be read is named in `unavailable` and `complete` is false, and nothing of another site is searched. It reads what the findings list reads plus `rest/wlanconf`, through the cache, and writes nothing. See [docs/web.md](docs/web.md#search-apiv1unifisitessitesearch).
- **Dashboard summary over the API (#244):** `GET /api/v1/unifi/sites/{site}/dashboard` is one small document for a first page: `status` (`critical`, `warning`, `ok` or `unknown`), `complete`, `stale` and the state of the `controller` (`ok`, `unreachable`, `certificate`, `key_rejected`), the findings counted by severity and by triage state (with the five open findings to look at first), the headline of the internet connection and Wi-Fi, device and client counts (online, offline, previously seen) and the newest notable events, each section with `available` so a section that could not be read is never shown as zero. A partial read, an answer served from an older cache or an unreachable controller is never `ok`; an unreachable controller is a `200` with every section unavailable, not an error. It reads what a full `diagnose` reads and no new endpoint; both roles read it. New JSON Schema `dashboard.v1.schema.json` (the document has `version` 1). See [docs/web.md](docs/web.md#dashboard-summary-apiv1unifisitessitedashboard).
- **A Docker image (#246, part 1 of #188):** a multi-stage `Dockerfile` (a placeholder web build stage, then wheels built from the checkout, then `python:3.13-slim` as the non-root user `hlp`, uid 10001, with `/data` as working directory and volume) that runs both the command line (`ENTRYPOINT ["hlp"]`, `docker run --rm homelab-probe --demo diagnose`) and the server (default command `serve --host 0.0.0.0 --allowed-host localhost --scheduler`, which needs no configuration: it starts in the setup mode and prints the setup token in its log). It sets `LOG_FORMAT=json`, has a `HEALTHCHECK` on `/healthz` (Python's standard library, no `curl`) and runs with a read-only root file system. `compose.yaml` publishes the port on `127.0.0.1` only, drops every capability, sets `no-new-privileges` and a `tmpfs` for `/tmp`, and has no setup token. `.dockerignore` lets only the copied files into the build context, so `.env`, `snapshots/` and the accounts can never reach the image. The image is not published yet. The CI job **Docker image** builds it on pull requests and runs `tools/docker_smoke.sh`; Dependabot now also watches the base image. See `docs/docker.md`.

### Changed

- **Clearer CLI help (#236):** general, connection and presentation options have their own sections, followed by alphabetical commands. A compact `COMMAND` placeholder replaces the repeated command list in usage; standard argparse semantics, descriptions and shell completion are preserved. Help remains unstyled, copyable text.
- The Docker section of `docs/scheduling.md` no longer carries its own Dockerfile and points to `docs/docker.md`: the scheduled run is `docker run --rm --env-file .env -v homelab-probe-data:/data homelab-probe diagnose --notify` (the image's default command is the server, so name the command, and mount the volume at `/data`, not `/data/snapshots`).
- **Terminal presentation controls (#233):** the global options `--color auto|always|never`, `--no-progress` and `--plain` (before the command), and an optional **`pretty` extra** (Rich: `pip install '.[pretty]'`). `homelab_probe/present.py` is the one policy: stdout and stderr are judged separately (terminal, `TERM=dumb`, UTF-8, width), `NO_COLOR` is honored, `--plain` beats everything, an explicit `--color always` beats `NO_COLOR`, and `--json`, `--csv`, `topology --format mermaid|dot`, `export` and `completion` are never styled or animated. Text from the network is rendered literally (never as markup) and cleaned of control characters. This is the shared foundation for the spinners, colored findings and headings that follow (#234, #235, #236): no command changes its output yet, and without the extra everything runs as before. See [docs/configuration.md](docs/configuration.md#terminal-styling---color---plain-and---no-progress).
- **Documentation bundle builder (#243, part of #187):** a development tool, not part of the package and not a command: `tools/build_docs.py OUT_DIR --tag vX.Y.Z` builds `docs.json` (pages grouped in the README's order, heading anchors as GitHub makes them, search text, links resolved to routes or to repository links at the tag) and copies the referenced images and the JSON Schemas, for the web interface's Docs page. Raw HTML, constructs outside the approved Markdown subset, missing images and broken links or anchors fail the build. See [docs/development.md](docs/development.md#development).

## [0.4.0] - 2026-10-06

### Added

- **Settings over the API (#186, part 1):** `GET` and `PUT /api/v1/settings` (administrators only; each value says where it comes from, and a threshold managed by an environment variable would be refused on write) read and change the `hlp.toml` that `diagnose` and `audit` use (thresholds and ignore rules). A change is validated by the loader every command uses (its own message in a `422`), keeps the file's comments (`tomlkit`, new in the `web` extra only), is refused with `409` when the file changed since it was read (a version hash, also checked right before the write), keeps the file's permissions, saves the old content as `hlp.toml.bak` and is audited as `settings.updated` (names and counts, never rule text). Administrators only, CSRF-protected. **`serve --read-only`** writes no file on this machine: the settings editor and the setup's `finish` answer `403 read_only`, and `/api/v1/meta` and the settings document say `read_only`. See [docs/web.md](docs/web.md#settings-apiv1settings).
- **Snapshots over the API (#186, part 2a):** `GET /api/v1/unifi/sites/{site}/snapshots` lists the saved snapshots of a site, `POST` saves one now (administrators, CSRF, audited as `snapshot.saved`, refused by `serve --read-only`; an optional `keep` prunes this site's oldest as `snapshot --keep` does) and `GET .../diff?old=&new=` compares two saved snapshots or one with the network now, in the document `diff --json` prints. Snapshots are named by bare file name only, and only those of the site are reachable. See [docs/web.md](docs/web.md#snapshots-apiv1unifisitessitesnapshots-and-diff).
- **Users over the API (#186, #221):** `GET`/`POST /api/v1/users` and `PATCH /api/v1/users/{username}` (role and/or disabled in one step) and `POST .../password`, for administrators only, with CSRF, the audit events the command line writes (one entry per change; `user.updated` when role and disabled change together), the last-administrator rule on every path, `serve --read-only` refusal, and sessions ended by a role, disabled or password change. See [docs/web.md](docs/web.md#users-apiv1users).
- **The scheduler (#186, #222):** `serve --scheduler` runs `diagnose` with notifications (`SCHEDULER_DIAGNOSE_MINUTES`, default 15) and takes snapshots with retention (`SCHEDULER_SNAPSHOT_HOURS`, default 24, 0 for never; `SCHEDULER_SNAPSHOT_KEEP`, default 30) inside the server, once it is set up. It uses the same notification state as cron, and the notification step now takes a **lock on that state** (`notify-state.json.lock`) in the command line too, so a scheduled run and a cron run never both announce a finding; a state that cannot be locked in two minutes stops the run with exit code 3 before anything is sent. The first scheduled run with no state records the current findings as already reported; a partial or failed read never changes the state. Each run is a `scheduler.run` log record with a run id and a fixed reason, never content. Not with `--read-only` or `--demo`. A stopping server makes a waiting job give up and a running one send and write nothing more. `snapshot` (and the API and the scheduler) now create a snapshot file exclusively, so a dangling symbolic link at its name is never followed. See [docs/web.md](docs/web.md#the-scheduler).
- **Status and the test notification (#186, #223):** `GET /api/v1/status` reports what the server has seen: the controller (`ok`, `unreachable`, `certificate`, `key_rejected` or `unknown`, and the last successful read), whether the last answer was stale and how many warnings it had, and the scheduler's jobs; an administrator also gets the failure kinds, the destinations by kind with the last delivery to each, the storage (data directory, audit log, `snapshots/`, free disk) and a `problems` list, all in fixed words. `POST /api/v1/notifications/test` sends one fixed test message to every configured destination, only when an administrator asks (CSRF, at most every 10 seconds), and reports a kind and a fixed reason per destination. The webhook payload schema gains the optional `test` key (true only in that message; `events` is then empty). See [docs/web.md](docs/web.md#status-and-the-test-notification-apiv1status).
- **Restoring a backup (#186, #226):** `POST /api/v1/backup/restore` replaces the settings, `.env`, accounts, certificates, notes and triage state with a backup as **one set** (nothing is merged), after the same checks as the preview. It needs an administrator, or the setup token on a server that is not set up (a fresh installation is restored this way; the preview accepts the token too), and is refused by `--read-only` and by `--demo`. Before replacing an existing installation it writes an encrypted **recovery backup** of the present state to `recovery/` (its own passphrase, typed twice; the newest three are kept, never pruned after a failure or while a restore is unfinished). Every session ends and the settings and controller service are made anew (an environment variable keeps winning over the restored `.env`); optional snapshots are added without deleting anything and the audit history of a backup is saved apart in `audit-imports/`, never over the present log. A journal and staged files make a restore recoverable: `hlp serve` completes or undoes an interrupted one before it reads the settings (a state it can do neither with stops the start with exit code 3), while it runs the routes that write files answer `503 restore_in_progress`, a running scheduled job is waited for and none starts, and it holds the locks of `.env`, the settings file, the accounts and the per-site files, which `hlp init` and the settings change now take too. Audited as `backup.restored` and `backup.restore_failed`. See [docs/web.md](docs/web.md#restoring-a-backup-apiv1backuprestore).
- **Encrypted application backup, export and preview (#186, #226):** `POST /api/v1/backup` (administrators, CSRF) downloads an encrypted backup of the application's own state: settings, `.env`, accounts, certificates, notes and triage (including those of devices and findings that are gone), and optionally the snapshots and the audit history. It is not a UniFi controller backup. The file is sealed with a passphrase typed twice (scrypt and AES-256-GCM from `cryptography`, a new dependency of the `web` extra only), holds a ZIP with a versioned manifest (format, data format, application version, categories, size and SHA-256 of each file) and cannot be opened without the passphrase, which is never stored or logged. `POST /api/v1/backup/preview` opens an uploaded backup, checks it completely (allowed member names only, sizes, manifest, the application's own readers, the site of every per-site file, an enabled administrator) and says what a restore would do without a secret in the answer; the names (never the values) of settings an environment variable keeps overriding are listed. Both change nothing and work with `--read-only`; audited as `backup.exported` and `backup.previewed`. See [docs/web.md](docs/web.md#backup-apiv1backup).
- **Notes (#186, #225):** `GET/POST /api/v1/unifi/sites/{site}/notes` and `PATCH/DELETE .../notes/{note}` keep short plain-text notes about a finding, a device or a client. A note belongs to `device:<MAC>`, `client:<MAC>` or `finding:<id>`, never to a name, so it follows a rename and is kept while the device is offline; it records its author (the login of the request), when it was written and last changed, and the findings list shows `note_count`. Stored per site in `snapshots/<site id>/notes.json` (owner-only, atomic, never through a symbolic link), limited to 4000 characters of cleaned text, 200 notes per subject and 5000 per site. Administrators only, audited as `note.added`, `note.edited` and `note.deleted` with the note id and the kind of subject (never the text or a MAC), refused by `--read-only`. An edit sends the `revision` it read and a stale one is `409 notes_conflict`; `GET .../notes/subjects` lists every subject with notes and its last-known name, present in the inventory or not; the findings list says `notes_available`. See [docs/web.md](docs/web.md#notes-apiv1unifisitessitenotes).
- **Findings with triage (#186, #224):** `GET /api/v1/unifi/sites/{site}/findings` lists the findings of a site in the order to look at them, each with a stable id (the check plus the MAC, or the subject when there is none), the reasons for its place (severity, the scope of the check, how long it has been known where there is a record), its triage state, what is not known, and general next checks with a documentation link. `PUT .../findings/{id}/triage` lets an administrator acknowledge a finding, snooze it until a date or reopen it; the finding stays in the list, acknowledged is not resolved, and an entry ends only when a complete read of every check (the scheduler's diagnose run) no longer shows the finding. The state is `snapshots/<site id>/triage.json`: ids, codes, states, who and when, never a name or a MAC. Audited as `triage.changed` without names or the note; refused by `--read-only`. See [docs/web.md](docs/web.md#findings-and-triage-apiv1unifisitessitefindings).

### Changed

It contacts nothing otherwise. See [docs/configuration.md](docs/configuration.md#guided-setup-init).

Every unsafe request needs the session's CSRF token and an `Origin` that matches the `Host`. Every route needs a login except `/`, `/healthz`, `/readyz` (now yes or no only), `/api/v1/meta` and the login itself, and a route that declares nothing needs one too. Failed logins are slowed down per address (up to 5 minutes) and per username (up to 30 seconds), never locked for good. The server refuses to start without an enabled administrator, `serve --demo` has a throwaway administrator whose password it prints once, proxy headers are no longer trusted, and the audit log records `auth.login`, `auth.login_failed`, `auth.throttled` and `auth.logout`. Errors are a code and a fixed sentence. `/api/v1/schemas` serves the JSON Schemas, which are now also shipped inside the wheel (`homelab_probe/schemas`). See [docs/web.md](docs/web.md).

A `Host` check, no CORS, a strict content-security policy on every response, GET only, and a request log that never holds the path asked for. See [docs/web.md](docs/web.md).

When the settings cannot be saved here (the environment sets them, the settings file is named by `--env-file` or `HLP_ENV`, a read-only volume) nothing is written and the answer is the finished `.env` and a compose snippet with a placeholder where the API key goes. The connection test now also lists the controller's sites. **Changed:** a server with settings but no enabled administrator no longer exits with code 3: it starts in an admin mode where the setup token may create the first administrator (and nothing else); `hlp web-user add` and a restart still work. The first tagged release. Everything since the fork is listed below.

**Tested against one controller (UniFi Network 10.6.106) only.** Most of the endpoints used are undocumented and

### Added

- **`--demo`** (before the command): runs any command on the packaged synthetic network, with no `.env`, environment variable or implicit settings file read, no controller contacted and nothing sent (an explicitly named `--config` is still used; `--notify`, `doctor`, `snapshot` and `diff` are refused with exit code 64). See [docs/configuration.md](docs/configuration.md#trying-it-without-a-controller---demo).

UniFi is the primary and, for now, only supported platform; the name leaves room for others. Nothing was released under the old name, so there is **no alias and the old names are not read**:
  - the distribution is `homelab-probe`, the Python package `homelab_probe`, the launcher `hlp.py`, the installed command `hlp`;
  - the settings file is `hlp.toml` (example: `hlp.example.toml`) and the variable that names the `.env` file is `HLP_ENV` (they were `unifi-sentinel.toml` and `UNIFI_SENTINEL_ENV`);

Nothing changes by default: `Warning: ...` lines and `--verbose` `[verbose] ...` lines are byte-for-byte what they were. New settings `LOG_LEVEL` (`DEBUG`, `INFO`, `WARNING`, `ERROR`) and `LOG_FORMAT` (`text` or `json`, one record per line with `ts`, `level`, `logger`, `msg`, `event`, `request_id`, `user`, `site` and the event's fields); a run has a `request_id` that also reaches the threads of a parallel read. Secrets (the API key, notification URLs, tokens and the mail account) and the values of `Authorization`/`Cookie` headers never reach a record; INFO and above never carry client names, MACs or addresses. `notify.delivery` and `watch.pass`/`watch.unavailable` are new records. See [docs/logging.md](docs/logging.md).
- **The tool talks to the Integration API first** (`/proxy/network/integration/v1`). The legacy endpoints are used
  only for data it lacks (per-port counters, client-to-port mapping, reservations, network and Wi-Fi settings,
  health), and the zone-based firewall comes from the v2 endpoints.
- **Layout:** the script is now a thin launcher over the `homelab_probe` package (`hlp.py`, or the
  `hlp` command after `pip install .`), commands are one registry, each command declares what it reads,
  and `diagnose` is a package with a module per topic. None of this changes the command line.
- **Reads run side by side** (up to 6 requests at once) and a client lookup reads far less; analysis is linear in
  the number of clients. Output and the order of warnings are the same as when reading one by one (`--parallel 1`).
- **Minimum Python is 3.10** (3.9 is no longer supported).
- **Errors exit with code 3** (earlier untagged versions exited 1 for every error), so `1` and `2` only ever mean findings.

  directory or a parent directory. A tool installed with `pip install .` now finds the `.env` the README describes.
- **Snapshot file names are in UTC** (`snapshot-YYYYMMDD-HHMMSSZ.json`); older local-time names are still read and
  ordered correctly.
- **`--show-ignored` lists each finding's code**, so it can be copied into an ignore rule.
- The version is written in one place, `homelab_probe.__version__`.
- **Documentation:** the README is now a short quickstart (what it is, install, configure, the commands with one example each, the exit codes) and the detail is in `docs/` (diagnose and audit, notifications, inventory, network views, configuration and troubleshooting, running on a schedule, examples, features, development). Historical README anchors remain at their original URLs, and output samples are generated from the checked-in fixture.

  certificate that is not usable as a CA bundle, and a host-name/SAN mismatch, instead of always saying the

- Notification setup errors link to the online guide, including for installed users outside a source checkout.
- Switch ports are matched on switches that report no `mac_table_count`, and offline devices keep their last uplink.

- Correct handling of 2.4 GHz channel 14 and the U-NII-4 channels (165 to 177) in the Wi-Fi channel plan.

### Security

- **Read-only by construction:** a test enforces that the controller client only issues GET requests and the one
  approved event-log query, and that the notification code never touches the controller client.
- **Output safety:** names that come from devices on your network are cleaned of control characters, line breaks,
  text-direction overrides and invisible characters before they are printed; exported CSV cells that a spreadsheet
  would run as a formula (`=`, `+`, `-`, `@`) get a leading apostrophe (`export` and `query --csv`).
- **Credentials:** the API key is never printed (it is stripped from response bodies and error text); a `.env` that
  other users can read gives a warning; an `http://` controller URL is refused unless `ALLOW_INSECURE_HTTP` opts in;
  notification URLs, tokens and the mail account are secrets that never appear in a message, error or log line.
- **Saved snapshots** are written owner-only into the git-ignored `snapshots/` and hold real MACs and IPs, so
  treat them like the `.env`.
- **Email** (SMTP) uses STARTTLS or implicit TLS with the certificate and host name verified, never sends a
  password without encryption, and its failures print a fixed reason, never the host, user or password.
